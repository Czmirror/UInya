# Admin screens

管理画面・業務画面・社内ツールなど、担当者がデータの登録・変更・削除・承認・送信を行う画面を作る・変える場合に適用します。
担当者の権限を付与・変更する機能、統計・集計の画面、データの出力（CSV等）を作る・変える場合も含みます。
一般利用者向けの画面（利用者に見せるランキング等の集計を含む）とゲームには適用しません（ゲームの操作説明は[Controls](controls.md)）。
目的は、操作する人が説明を探さずに迷わず使え、取り消せない操作を誤って実行しないことです。
どの権限・統計・出力を作るかは、このルールでは決めず、projectの仕様書で決めます。ここには作るときに守ることだけを書きます。

既存ルールとの分担:

- 入力の条件表、server側の最終検証、利用者向けの安全なエラー文言は[Input validation](input-validation.md)。
- 見た目の水準と色・余白の置き場所は[UI visual](ui-visual.md)。
- label・エラー表示・キーボード操作・focus、通信中・失敗・空の状態、二重送信は[Web](../stacks/web.md)。
- 認可、権限が変わった後のsession IDの作り直しは[Security](security.md)。操作の記録は[Logging](logging.md)。
- 個人情報の置き場所と最小化は[Sensitive data](sensitive-data.md)。DBの権限と高負荷の副作用は[SQL](../stacks/sql.md)。
- 定期的な事前集計は[Scheduled jobs](scheduled-jobs.md)。
- 利用者の投稿の確認・解除、NGワードのリストを更新する画面は[User content](user-content.md)も読む。
- 仕様書と用語は[Workflow](workflow.md)の「仕様書」。

## 画面の中の説明

- 画面ごとに、何をする画面かを1文で示す。
- 入力欄にはlabelを付け、近くに入力例と制約（必須か、形式、上限、単位）を書く。
  値は[Input validation](input-validation.md)の条件表と同じにし、可能ならschemaや定数から表示して、画面に別の値を書かない。
- 必要な情報をツールチップ（マウスを乗せたときだけ出る説明）だけに置かない。タッチやキーボードでは見えないことがある。
  補足に使う場合は、キーボードのfocusでも出るようにする。
- 画面の用語は仕様書の「用語」に合わせる。DBの列名やenumの値など、内部の名前をそのまま画面に出さない。
- 一覧が空のときは、何をすれば項目ができるかを示す。読み込み中・失敗・値の欠けの表示は[Display states](display-states.md)に従う。

## 取り消せない・影響が大きい操作

対象は、削除、外部への送信（メール・通知・webhook）、公開、一括更新、権限の変更、返金・決済などの業務操作です。
どの操作が当たるかは仕様書に書きます。AIが決めきれないものは、提案する仕様として人間に確認します。
メールの一斉送信では、送信の仕組み（本番以外の送り先、二重送信の防止、配信停止）も[Email](email.md)に従います。

- 実行前の確認で、対象（名前・件数）と影響（誰に何が届くか、元に戻せるか）を示す。「よろしいですか？」だけの確認にしない。
- 特に影響が大きい操作（全件削除、本番データの一括変更など）では、対象名の入力など、確認を読み飛ばせない形を検討する。
- 元に戻せる仕組み（論理削除、送信前の猶予、取り消しボタン）を設けるかは、提案する仕様として人間が決める。
- 誰が・いつ・何を実行したかを記録するかを計画で決める（[Logging](logging.md)）。
- 権限のない操作のボタンを隠すのは表示の補助で、認可の代わりにしない。server側で毎回認可する（[Security](security.md)）。

## エラーと結果の表示

- エラーは、何が起きたかと、次に何をすればよいか（どの項目を直すか、再試行してよいか、誰に連絡するか）を書く。
  内部情報（stack、SQL、内部ID）は出さない（[Input validation](input-validation.md)）。
- 成功したときも、何が起きたか（件数、送信先）を示す。
- 一括操作で一部だけ失敗した場合は、成功と失敗を分けて示し、失敗したものを特定できるようにする。

## 権限の付与・変更

- 役割（role）と、それぞれができる操作の表を仕様書に書く。表にない組み合わせは拒否する。新しい役割・操作を足すときは、表を同じPRで更新する。
- 新しい担当者の既定は、最も権限の小さい役割にする。全権限の役割を既定にしない。
- 自分の権限を自分で上げられないようにする。付与できるのは、付与する人が持つ権限の範囲までにする。どちらもserver側で確かめる（ボタンを隠すだけにしない）。
- 最後の管理者を削除・降格できないようにする。組織・tenantがある場合はその単位で数える。
- 剥奪がいつ効くか（次の要求からか、session・tokenの期限までか）を計画に書く。すぐに効かせる必要があれば、[Security](security.md)の「サーバー側の記録か失効の仕組み」に従う。
- 付与・剥奪は監査イベントとして記録する。項目は、実行した人、対象の人、変更前と変更後の役割、時刻、結果（[Logging](logging.md)）。記録を画面から見られるようにするかは仕様で決める。
- 権限の方式（RBAC・ABAC等）は自作せず、frameworkやlibraryの既存の仕組みを使う（[Libraries and dependencies](libraries.md)）。
- testは、役割ごとに許可・拒否される操作、自己昇格の拒否、自分より上の権限の付与の拒否、最後の管理者の削除・降格の拒否、剥奪後の要求の拒否を含める。

## 統計・集計・データの出力

- 集計の定義を仕様書に書く。期間の始まりと終わりを含むか、時刻帯（timezone）、日・月の境界、除外する対象（test用のデータ、キャンセル、削除済み等）、重複の数え方。
  AIが決めきれない定義は、提案する仕様として人間に確認する（[Input validation](input-validation.md)と同じく業務上の値を発明しない）。
- 画面には、集計の期間と時刻帯を表示する。事前に集計した値を見せる場合は、いつ時点の値かも表示する。
- 目的に足りるなら、個人を特定できる項目を出さず、集計値で見せる。個人単位の一覧が必要な場合は、見られる役割を仕様で限る。
- 件数が少ない区分では、集計値からでも個人が分かることがある。最小件数を設けて伏せるかは、提案する仕様として人間が決める。
- CSV等の出力・ダウンロードは、画面の表示とは別の操作として、server側で毎回権限を確かめる。URLを知っていれば誰でも取れる形にしない（要求ごとの認可、期限付きのURL）。
- 出力する列は、その人が画面で見られる範囲を超えない。個人情報を含む出力は、誰が・いつ・何を出力したかを記録する（[Logging](logging.md)）。
- 利用者が入力した値をCSVに出す場合は、`=`、`+`、`-`、`@`、タブ、CRで始まる値が表計算ソフトで数式として実行されないようにする（先頭に`'`を付ける等。[OWASP CSV Injection](https://owasp.org/www-community/attacks/CSV_Injection)）。
- PDFで出力する場合は、[PDF output](pdf-output.md)にも従う。
- 重い集計を、要求のたびに本番の主DBで実行しない。読み取り専用の複製、事前の集計、期間・件数の上限、timeoutから選び、計画に書く。大きな出力は非同期で作り、できたら知らせる。
- testは、期間の境界（始まり・終わり・時刻帯の切り替わり）、0件、権限のない人の出力の拒否、数式で始まる値の出力、上限を超える要求を含める。

## 運用手順書

- 手順書の置き場所は、ステアリング`.harness/steering/project.md`の「設計・運用の文書」に書く。ステアリングがない導入先では`AGENTS.md`に書く。
- 手順書があるprojectでは、画面の操作・手順・権限が変わる変更で、手順書を同じ変更（同じPR）で更新し、完了報告に更新した箇所を書く。
- 手順書がないprojectでは、AIは勝手に作らない。作るかどうかを計画で提案し、人間が決める。
- 本格的なヘルプページ、FAQ、操作動画を作るかはprojectが決める。既定は、画面の中の説明と手順書までとする。

## 検証

- 機能試験仕様書を作る場合は、取り消せない操作の確認表示（対象・件数・影響が出ること、確認を取り消すと何も起きないこと）と、エラー時の表示をケースに含める。
- 画面の説明・確認・エラーの表示は、自動検証とは別に人間確認として完了報告に書き、可能ならスクリーンショットを添える（[UI visual](ui-visual.md)の「確認と報告」）。
