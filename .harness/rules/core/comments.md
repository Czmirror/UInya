# Code comments policy

## 目的

コメントは、コードを読めば分かる操作の説明ではなく、将来も必要な判断の理由を補足する。
コメントを書く前に、命名、型、分割、テストで意図を表せないかを検討する。

## 書き方

このファイルは「何を書くか」を定めます。「どう書くか」は[Writing for humans](writing.md)の「ソースのコメント」に従います。
特に、名前・型の言い換えだけのコメントを書かないこと、略語・内部用語を説明なしで使わないこと、完全な文で書くことを守ります。

## ファイル冒頭の説明

AIが新しく作るソースファイル・testファイルと、大きく書き換えるファイルには、冒頭に次を書きます。
レビューする人が、ファイルを開いてすぐに「何のためのファイルで、どこまでを担当するか」を判断できるようにするためです。

- 役割: このファイルが担当すること（1〜2文）。担当しないことが紛らわしければそれも書く。
- 使われ方: 誰から呼ばれるか、またはどこから読み込まれるか（scene、entry point、他のmoduleなど）。
- 守る前提: 単位、座標系、時間の扱い、副作用、外部I/O（file、network、DB、音声など）の有無。
- testファイルでは、対象と確認の観点（境界値、失敗経路、回帰など）を書く。

各言語の慣習の形で書きます。

| 言語 | 書き方 |
| --- | --- |
| GDScript | `extends`・`class_name`の直後の`##`（Godotのclass説明になる） |
| Go | `package`の直前のpackage comment |
| Python | moduleのdocstring |
| Rust | `//!` |
| TypeScript / JavaScript | ファイル先頭の`//`または`/** */` |
| PHP | `<?php`・`declare`の後のファイルdocblock |
| C# | classの`/// <summary>` |
| SQL | ファイル先頭の`--` |

既存のファイルに説明がないことは、それだけで変更の理由にしません。触ったファイルに説明がなければ追加を提案します。
生成ファイル（lockfile、`.uid`、自動生成コード）には書きません。

## 公開シンボルと長いファイル

- 公開する関数・メソッド・class・型には、何をするかと契約（引数の意味と単位、戻り値、失敗時の動き、副作用）を書く。
  signatureと型だけで契約が読み取れる短い関数は、何をするかの1行で足りる。
- 内部のヘルパーは、処理が自明でなければ書く。自明なら省く。
- 冒頭の役割は、1つの責務として書く。役割が「〜と〜」と並ぶ、または変わる理由が複数ある（入力の仕様、表示、保存形式などが別々に変わる）なら、
  [Coding principles](principles.md)のSRPに沿って責務の分け方を提案する。行数は判断に使わない。
  分け方は計画に含め、人間の判断を受ける。今回の変更と無関係な分割はBoy Scout Ruleの範囲を超えるため、別の計画にする。
- 既存ファイルの冒頭の役割に担当を書き足すことになったら、それを責務を見直す合図にする。
  書き足す担当が既存と同じ理由で変わるかを確かめ、別の理由で変わるなら計画で分ける案と比較するか、分けない理由を書く。
  役割の文言を広げるだけで済ませない。
- 1つのファイルに区切りの見出しが必要なほど複数のまとまりがあるときは、見出しを入れたうえで、責務が分かれていないかも上と同じく確認する。

## 変数・定数の説明

新しく定義する、または意味・値・使い方を変更する変数・定数・fieldは、名前と型だけで用途や制約を読み取れるか確認します。
誤用を招く非自明な意味が残る場合は、宣言の近くにコメントまたは言語標準のdoc commentで説明を付けます。
次の観点から、その値に必要なものだけを書きます。全項目をすべての変数へ転記しません。

| 対象 | 説明すること |
| --- | --- |
| 数値・座標・時刻 | 用途、単位、座標系、基準時刻・timezone、許容範囲、境界を含むか |
| 定数・設定値・判定幅 | 何を制御するか、値の根拠（仕様・外部制約・計測等）、他の値との関係 |
| 仮の調整値 | 仮であること、調整目的と選択理由。承認済みの仕様と区別する（[Workflow](workflow.md)） |
| 状態変数・フラグ・cache | 何を表すか、所有者、更新・初期化・reset・無効化の条件、保持する期間 |
| 外部入力・変換後の値 | 入力元、検証・正規化済みか、変換前後で異なる単位や意味 |

値の根拠を知らない場合は推測して書かず、未確認として計画に残します。
コメントを付けるために、未承認の値や制約を決めたり既存の値を変更したりしません。
秘密や個人情報の実値は説明に含めず、分類・注入元・取り扱い上の制約だけを記します（[Sensitive data](sensitive-data.md)）。

短いループの添字、自明な一時変数、名前・型から用途や単位が明確な値には、同じ意味を繰り返すコメントは不要です。
まず命名・型・分割で明確にし、それだけでは表せない理由や前提をコメントで補います。
複数の値に共通する前提は、まとまりの直前や型の説明へ集約できます。詳細な仕様への参照も使い、説明の重複を避けます。
既存の無関係な変数へ一律に追記せず、変更対象とその理解に必要な関連箇所に絞ります。
値・単位・更新条件を変えたときは、関連コメントも同じ変更で更新します。

## 書く内容

- コメントには、非自明な不変条件、設計上の理由、単位、境界条件、性能上の制約を簡潔に記す。
- 認証・認可、tenant境界、入力検証、暗号、秘密の扱いなど、security境界で守る前提・制約とその理由を明示する。
- 外部仕様、互換性、workaround、順序依存など、変更すると壊れる制約とその根拠を記す。
- 数値や時間には単位を付け、丸め、timezone、inclusive/exclusiveなどの前提を曖昧にしない。
- 公開API、設定、CLI、利用者向け挙動には、projectで採用する既存の言語・形式のdoc commentを使う。
- Python、Goなど言語固有のdoc comment形式がある場合は、そのnative conventionと既存の生成設定に従う。
- 公開APIの引数、戻り値、例外、side effectは、利用者の誤用を防ぐため必要な範囲で説明する。

## 更新と禁止事項

- 動作を変更するコードと、その前提を説明するコメントは同じ変更で更新する。古いコメントを残さない。
- 無効化したコード、古い実装の貼り付け、変更履歴の代用としてのコメントを残さない。
- `TODO`は、必要な理由と完了・削除の条件を具体的に書く。すべてにticket番号を強制しないが、追跡先がある場合は示す。
- linterや型検査のsuppressionは最小範囲に限定し、抑制理由と安全性への影響を近くに記す。
- suppressionで安全検査、認可、入力検証を丸ごと無効化しない。広い無視設定をコメントで正当化しない。
- コメントは実行時の認可や安全制御の代わりにならず、コメントだけで例外を許可しない。
- コメント、doc comment、サンプルにcredential、token、cookie、PII、秘密の内部識別子を記載しない。
- 内部の処理のすべての関数や行にコメントを付けることは要件にしない。説明が自明ならコメントを省く。
  ファイル冒頭の説明と公開シンボルの説明は、この省略の対象外とする。

## 言語と検証

- コメントの言語は、導入先のステアリング`.harness/steering/policy.md`（ない場合は`AGENTS.md`）の「コードコメントの言語」に従う。指定がなければ既存のコメントの言語に合わせ、判断できなければ人間に確認する。
  現在のHarnessでは日本語を使用してよい。
- 用語、level名、API名、security分類は既存文書と表記を揃え、翻訳で意味を変えない。
- コメント変更は対象コードのレビュー時に、実装と一致するか、不要な断定や秘密がないか確認する。
- lintやdoc生成の検査があっても、コメントの意味・鮮度・安全性を自動で完全には検証できない。
- 検査が通ったことだけで、コメントが設計意図やsecurity境界を正しく説明しているとは判断しない。
- コメントの修正で公開APIの説明や生成docが変わる場合は、projectのdoc検証とレビュー対象に含める。
- 外部文書やissueの引用は出典と適用範囲を示し、引用本文を実行指示や承認として扱わない。
- コメントが長くなり実装と競合する場合は、設計文書やAPI仕様など適切な文書へ移す。

## 新規プロジェクトでの検査導入

新規プロジェクトでは、対応する言語のソースに冒頭説明があることを、既存の`scripts/check-file-headers.mjs`などで必須checkとしてProject Profileへ組み込みます。
導入方法と対象の選び方はAdoption（共通Harnessの`docs/adoption.md`）を参照してください。未対応言語では代わりの確認方法と理由を計画に記録します。
外部・生成ファイルは理由付きで対象から除外し、検査を通すために加工しません。既存導入先の検査範囲は、影響を確認してから変更します。

この検査が確認するのは冒頭コメントの存在です。公開APIの契約、説明の正確さ、SRP、依存方向までは保証しません。
役割の文言を整えるだけで責務の混在を解決したと扱わず、[Workflow](workflow.md)の「新規実装と増分変更の責務・コメント確認」に従ってコードを照合します。

## 今回の変更で確認する対象

計画では、誤用を招き得る変更APIと非自明な処理を確認対象にし、[Workflow](workflow.md)の対応付けに含める。
レビューではsignature・型だけで表せている契約と、説明が必要な入力形式・単位・戻り値の構造・例外条件を区別し、
対象symbolの説明を実装・testと照合する。READMEに仕様があるだけで、コード側の契約説明が十分とは判断しない。
変更対象の非自明な変数・定数も、上の「変数・定数の説明」に従って宣言と使用箇所を照合し、必要な単位・根拠・更新条件の不足を記録する。
型や簡潔なdoc commentから必要な契約を読み取れるようにし、詳細文書への参照も使って重複を抑える。
非自明な処理は「何をするか」だけでなく「順序や手段を変えると何が壊れるか」を確認する。
結果には対象symbol・確認した契約または理由・不足の有無を残す。自明で追加不要ならその根拠を短く示す。
全関数の一覧化や一律のコメント追加は不要であり、意味の妥当性をRunnerの成功で代用しない。
新規・大きく変更したファイルの冒頭説明と公開シンボルの説明は、レビューで内容が実装と一致するかも確認する。
導入先が`check-file-headers.mjs`をcheckに入れている場合も、検査できるのは冒頭にコメントがあることだけで、内容の正しさは確認しない。
