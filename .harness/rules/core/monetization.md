# Monetization

広告、アフィリエイトのリンク・紹介記事、寄付・投げ銭のリンク、有料機能・販売・ゲーム内課金を追加・変更する場合と、公開するWebサイト・アプリ・ゲームを新しく作る場合に適用します。
目的は、収益化を後から足して画面や告知を作り直さないこと、広告であることを隠さないこと、広告で操作や遊びを壊さないこと、開発中の操作で広告のアカウントを止められないことです。

どの手段で、いくら稼ぐかは人間が決めます。AIは候補と注意点を示し、法令に当たるかどうかを断定しません。

既存ルールとの分担:

- 決済情報の置き場所と決済代行のtokenは[Sensitive data](sensitive-data.md)、決済手段の登録の回数制限・カードテスティング・webhookの署名検証は[Security](security.md)。
- 本番の判定、告知・同意の決め方、計測は[Analytics](analytics.md)。
- 読み込みの目標とCLS（読み込み中の表示のずれ）は[Performance](performance.md)、COEPとゲーム投稿サイトのiframeは[Web delivery](web-delivery.md)。
- ゲームの一時停止は[Controls](controls.md)、セーブデータは[Save data](save-data.md)。
- 広告サービス・ASP（広告の仲介業者）・販売サイトの管理画面の操作の承認は[Safety](safety.md)。

## 収益化するかを先に決める

- 公開するWebサイト・アプリ・ゲームを新しく作る計画では、「収益化: 予定なし / 予定あり（手段）」を1行書く。決めるのは人間で、AIは下の一覧から作品に合う候補を2〜3個、注意点と一緒に示す。後から広告を入れると、広告枠の場所、プライバシーポリシー、ゲームの区切りを作り直すことになるため。
- 「予定なし」でもよい。決めた内容はステアリング`tech.md`の「収益化」に要点だけを書く。

候補の一覧:

| 手段 | 向いているもの | 主な注意 |
| --- | --- | --- |
| ディスプレイ広告（Google AdSense等） | アクセスの多いWebページ | 表示のずれ、読み込みの重さ、cookieの告知、自分のクリック |
| ゲーム内広告（AdSenseのH5 Games Ads等） | ブラウザーゲーム | 画面全体の広告は自然な区切りだけ。見ると報酬がもらえる広告（リワード広告）も使える |
| アフィリエイト（Amazonアソシエイト、楽天、ASP） | 紹介記事、使っている機材・本の紹介 | 「広告」「PR」の表示、体験を作らない |
| 寄付・投げ銭（GitHub Sponsors、Ko-fi等） | ポートフォリオ、無料のゲーム・ツール | お礼の特典を付けると販売に近くなる |
| ゲーム投稿サイトでの販売・収益分配（itch.io、Poki、CrazyGames等） | ブラウザーゲーム | 投稿先ごとに外部の広告・課金・リンクの可否と専用SDKが決まっている |
| 有料ダウンロード・有料版（itch.io、Steam、BOOTH等） | ゲーム、素材集 | 販売サイトが決済を持つので、決済を作らずに済む |
| 有料機能・月額課金（決済代行） | Webアプリ | 特定商取引法の表示、決済情報、解約・返金の流れ |
| ゲーム内課金・ゲーム内通貨・ガチャ | 継続運営のゲーム | 法令の論点が多い。下の「有料機能・販売・ゲーム内課金」 |

## 広告・PRであることを表示する

- アフィリエイトのリンク、提供を受けた物の紹介、依頼を受けた紹介には、「広告」「PR」などの表示を、その内容の近く（記事の冒頭、リンク集の見出しの横など）に、周りの文字と同じ程度の大きさと濃さで付ける。ページの末尾だけ、小さい・薄い文字だけ、長い文章やハッシュタグの中に紛れさせる、は不十分。2023年10月から、事業者が関わる宣伝を宣伝と分からない形で出すこと（ステルスマーケティング）は景品表示法の違反で、アフィリエイトの記事は消費者庁の運用基準で例に挙がっているため。
- 冒頭で「広告」と書きながら、本文で「広告ではない個人の感想」と書くような、食い違う説明をしない。
- 広告のプログラム（Amazonアソシエイト等）が決まった文言の表示を求める場合は、その文言をサイトに置く。文言はプログラムの規約の最新版から写し、AIの記憶で書かない。
- アフィリエイト・広告のリンクには`rel="sponsored"`を付ける。Googleが、対価のあるリンクに付けるよう求めているため。
- 紹介文は、人間が実際に使った・確かめた事実だけを書く。体験・感想・数値・順位を作らない。「最安」「一番」「必ず効く」などの表現は、根拠を人間に確かめてから使う。根拠のない強調は景品表示法の別の違反（実際より良く見せる表示）になりうるため。
- 商品の一覧や他人の文章を並べただけのページを作らない。プログラムの規約で独自の解説を求められることがあり、利用者にも価値がないため。
- 法令に当たるかどうかは断定しない。表示の場所と文言の案を示し、人間が決める。

## 広告の置き場所（Web）

- 広告の枠は、読み込む前から大きさを確保する。広告が後から入って本文やボタンがずれると、押し間違いが起き、CLSも悪くなるため。
- 広告をボタン・リンク・入力欄・ゲームの操作部分の近くに置かない。広告を記事やメニューと見分けにくい見た目にしない。「クリックして応援」など、広告を押すことを促す文言を書かない。誤クリックを誘う配置は広告サービスの規約で禁止され、収益やアカウントの停止につながるため。
- 広告は本文の表示を待たせない方式（非同期の読み込み）で読み込む。広告を入れる前と後で、[Performance](performance.md)の目標を測って比べる。
- COEPを付けたページでは、広告が出ないことがある（[Web delivery](web-delivery.md)）。両方が必要なら、計画で人間に示す。

## ゲームの広告

- 画面全体の広告は、ステージの合間・ゲームオーバーの後など、自然な区切りだけに出す。遊んでいる最中、起動の直後、別の広告を閉じた直後、毎回の操作の後には出さない。
- 広告を出す前にゲームを一時停止して音を止め、広告が閉じたら元に戻す。一時停止は、タブの切り替え等の自動の一時停止（[Controls](controls.md)）と同じ仕組みを使う。
- リワード広告は、見るかどうかをプレイヤーが選べるようにし、見なくてもゲームを最後まで遊べるようにする。
- 広告が出ない場合（広告ブロッカー、在庫切れ、読み込みの失敗）でも、ゲームを止めずに先へ進める。そのときの報酬の扱いは仕様で決める。
- 出す回数の上限（例: 3分に1回まで）を仕様に書く。
- ゲーム投稿サイト（unityroom、itch.io、Poki、CrazyGames等）で配信する場合は、外部の広告・課金・外部リンクの可否と、専用SDKの要否を投稿先の規約で確かめてから計画に書く。規約に反すると作品の公開を止められるため。

## 開発中は本番の広告を出さない

- ローカル・プレビュー・ステージング・testでは本番の広告を読み込まず、広告サービスのtest用の広告か、同じ大きさの仮の枠を出す。本番かどうかは[Analytics](analytics.md)と同じく、URLのscheme・host・pathを照合して決める。自分で本番の広告を表示・クリックすると不正なクリックと判定され、アカウントが止まることがあるため。
- 単体testで、本番以外では本番の広告を読み込まないことを確かめる。
- 広告のID（AdSenseの`ca-pub-`で始まる値）やアソシエイトのIDは、ページに出る公開の値で秘密ではない。広告サービス・ASP・販売サイトの管理画面の操作（設定の変更、審査の申請、支払い情報の変更）は、[Safety](safety.md)の承認が必要な外部操作として扱う。
- 有料の広告（SNSの広告等）からアフィリエイトのリンクへ誘導しない。プログラムの規約で成果の対象外になることがあるため。誘導する場合は、規約を人間が確かめる。

## 告知と同意

- 広告・アフィリエイト・寄付のサービスを新しく入れる・変える場合は、プライバシーポリシーと外部送信の説明（何を、どの会社へ送るか）の更新を計画に書き、人間が決める。広告はcookie等で利用者の情報を広告会社へ送るため。考え方は[Analytics](analytics.md)の「告知・同意と管理操作」と同じ。
- 欧州などからのアクセスに個人に合わせた広告を出す場合の同意の画面（CMP＝同意を管理する仕組み）や、子ども向けの作品で個人に合わせた広告を止めるかどうかも、要否を計画に書いて人間が決める。
- `ads.txt`（そのサイトで広告を売ってよい会社の一覧。サイトの一番上の階層に置く）は、広告サービスが示す内容をそのまま置き、AIが内容を作り変えない。

## 有料機能・販売・ゲーム内課金

- まず、決済を自分で作らずに済む方法（販売サイト、ゲーム投稿サイトの販売機能、決済代行が用意する支払いの画面）を候補に出す。作るものが減り、決済情報の事故も減るため。
- 自分で作る場合は、[Sensitive data](sensitive-data.md)の「決済情報」と[Security](security.md)の「重要な情報の更新」「webhookの受信」に従う。
- 販売する場合は、特定商取引法の表示（販売者の名前・連絡先・価格・支払いと引き渡しの時期・返品の扱い等）のページと、申し込みの最後に内容を確かめる画面が要るかを計画に書き、人間が決める。個人で販売する場合の住所・電話番号の載せ方（請求があれば開示する等）も人間が決める。
- ゲーム内通貨（前払いで買う通貨）、ガチャ、期間限定の販売は、AIは確認が必要な論点として挙げるだけにし、人間が専門家の確認を含めて決めるまで実装を始めない。主な論点:
  - 資金決済法: 前払いで買うゲーム内通貨は「前払式支払手段」に当たることがあり、使われていない残高が一定額を超えると届出などが要る。
  - 景品表示法: 特定の組み合わせをそろえると景品がもらえるガチャ（コンプガチャ）の禁止、実際より有利に見せる表示の禁止。
  - 業界団体の指針: ガチャの提供割合の表示、未成年の課金の上限。
- 購入・課金の状態は端末のセーブデータだけに置かず、正しい記録をサーバーか販売サイト側に持つ。端末のデータは書き換えられるため。

## 確かめ方と報告

- 実際のブラウザーで、本番以外で本番の広告が読み込まれないこと、広告の枠で表示がずれないこと、広告が出ない状態でもゲームが進むこと、広告の表示中にゲームが止まり音が鳴らないことを確かめる。
- 本番での広告の表示と収益の計上、アフィリエイトの成果の計上は公開前に確かめられない。完了報告とPRに未検証として書き、公開後に人間が管理画面で確かめる。

## 扱わないこと

- どの手段で、いくら稼ぐかの判断。
- 税金・確定申告・インボイス、契約の交渉。
- 広告の単価や収益を上げるための試行（必要なら[Analytics](analytics.md)の測定の仕様で扱う）。

## 記録する場所

収益化の有無、使う手段とサービス、広告・PR表示の場所、本番の判定方法、告知の場所は、ステアリング`.harness/steering/tech.md`の「収益化」に要点だけを書きます。
ステアリングがない導入先では`AGENTS.md`に書きます。
