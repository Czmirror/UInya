# Game replay

ゲームのロジック・乱数・入力処理を設計・変更する場合と、ゲームのバグを調べる場合に適用します。
現在の対象は[Unity](../stacks/unity.md)と[Godot](../stacks/godot.md)です。ブラウザーのゲームやBevy等は、導入先の`AGENTS.md`またはステアリングで対象に加えられます。
目的は、seedと入力からプレイを再現できるようにして、AIがバグを再現・特定・回帰testにできるようにすることです。
エンジン固有の乱数・tick・ロジックの置き場所は、各stackのルールに書きます。

既存ルールとの分担:

- 表示なしのリプレイ・botと、実際のscene・画面での確認の区別は[Runtime verification](runtime-verification.md)。
- 貼り付けたリプレイ文字列の検証は[Input validation](input-validation.md)。
- セーブデータの保存・互換は[Save data](save-data.md)。リプレイはセーブデータとは別に扱う。
- プレイテストのプレイ記録（どこで詰まったか・やめたか）は[Analytics](analytics.md)。記録にリプレイ文字列を含めると、詰まる場面を再現できる。
- ロジックと表示の境界の設計は[Design boundaries](design.md)。

## 用語

- リプレイ文字列: 形式のversion、buildの識別子、seed、設定、tickごとの入力をまとめ、文字列にしたもの。貼り付けるとプレイを再現できる。
- 状態ハッシュ: 一定tickごとのゲーム状態のchecksum。再生中に記録と比べ、結果がずれたtickを特定する。回帰testの期待値にも使う。
- bot: 表示を通さず、ロジックへ直接入力を与えてプレイするプログラム。

## 採用の判断

この仕組みは、ロジックの構造に関わる設計の判断です。採用するかどうかは人間が決めます。

- 新しいゲームや、ロジックを大きく作り直す設計では、AIが採用を計画で提案する。
- 既存のゲームへの後付けは、影響範囲と段階（例: 乱数のseed管理だけ先に入れる）を示し、承認なしに始めない。
- 決めた内容は、ステアリング`.harness/steering/tech.md`の「再現・リプレイ」に書く。ステアリングがない導入先では`AGENTS.md`の同じ項目に書く。
- 採用しない場合も、その旨と代わりの再現手段（ログ、デバッグ用の状態の書き出し等）を記録する。

以下の節は、採用した導入先で守る内容です。

## 表示とロジックの分離

- ゲーム状態の更新を「今の状態とそのtickの入力から、次の状態を作る」形にする。
- ロジックは描画・音声・UI・sceneの部品に依存させず、表示なし（headless、Node等）で実行できるようにする。
- 表示はロジックの状態を読んで描くだけにし、表示側の処理でゲーム状態を変えない。
- 演出だけに使う値（画面の揺れ、particle等）は、ロジックの状態に含めなくてよい。

## 決定論

- ロジックは固定tickで進める。可変のframe時間をロジックへ直接渡さない。
- 乱数は、seedを指定した専用の生成器から取る。共有のグローバル乱数をロジックで使わない。
  用途ごと（敵の出現、ドロップ等）に生成器を分けると、片方の変更が他方の結果を変えにくくなる。
- 現在時刻、frame rate、辞書・集合の列挙順、非同期処理の完了順、組み込み物理エンジンの結果に、ロジックを依存させない。
  依存が残る場合は、その範囲と、再現できない条件を記録する。
- 浮動小数点の計算結果は、platform・build・ブラウザーが違うと一致する保証がありません。
  同じbuild・同じplatformでの再現を基本とし、platformをまたぐ再現が必要なら、整数・固定小数点の採用などを人間と決める。

## リプレイ文字列

- 含める内容: 形式のversion、buildの識別子（revision等）、seed、ゲームの設定、tickごとの入力、一定tickごとの状態ハッシュ。
  同じ入力が続く区間はまとめて短くする。
- 開発版では、リプレイ文字列をクリップボードへコピーでき、貼り付けて再生できるようにする。長くなる場合はファイルでも扱えるようにする。
- 読み込みは外部入力として扱い、[Input validation](input-validation.md)に従って大きさの上限、version、値の範囲を検証する。
  読み込むとコードの実行やobjectの生成につながる形式を使わない。
- 対応しないversionやbuildのリプレイは、エラーとして知らせる。別の結果になると分かっている再生を、黙って続けない。

## bot

- AIに、ロジックを直接操作するbotを作らせる（決めた手順で動くもの、seed付きのランダム入力など）。
- botは表示なしで多数回まわし、crash、不変条件の違反（例: HPが負、移動できない位置にいる）、進行不能を検出する。
- 問題を見つけたら、そのプレイのリプレイ文字列を残し、報告に添える。
- botの実行回数や長さは、通常のtestの時間に収まる範囲で決め、長い実行は別のcheckに分ける。

## バグの再現と修正

1. バグ報告にリプレイ文字列を添えてもらう。なければ、手順からリプレイを作れるか試す。
2. 表示なしで再生し、記録した状態ハッシュとの比較と不変条件から、問題の起きたtickを特定する。
3. 原因を直したら、そのリプレイを回帰testとして残す。期待値には最終状態ハッシュや不変条件を使う。
4. 状態ハッシュが記録とずれた場合は、ロジックの変更か非決定性かを切り分け、非決定性なら原因を直す。

ロジックを意図して変えると、既存のリプレイの結果が変わることがあります。
その場合は計画で影響を示し、回帰testの期待値の更新は人間の確認を得てから行います。期待値を黙って書き換えて通しません。

## 公開版での扱い

- リプレイのコピー・読込を製品版にも出すか、ランキング・共有に使うかは人間が決める。
- 利用者から受け取ったリプレイは信頼しない。ランキング等に使うなら、server側で再計算するなど検証の方法を計画で示す。
- リプレイにプレイヤー名など個人に関する情報を含める場合は、[Sensitive data](sensitive-data.md)を適用する。

## 実動検証との関係

表示なしのリプレイ・botは、[Runtime verification](runtime-verification.md)の「隔離したtest」に当たります。
描画・入力・音声・platform固有の動作の確認の代わりにはしません。
リプレイを実際の表示付きで再生して観察した場合は、実際のscene・画面での確認の手段として使えます。

## Webでの扱い

- ブラウザーのゲームでも同じ考え方を使える。ロジックを表示から分けた関数にすれば、Node等でbotをまわせる。
- `Math.random()`・`Date.now()`・`requestAnimationFrame`のframe時間を、ロジックへ直接使わない。seed付きの乱数と、固定tickでの積み上げで進める。
- `Math.sin`等の数学関数は、ブラウザーの実装によって結果が異なることがあるため、ブラウザーをまたぐ再現は保証しない。
- クリップボードへの書き込みは、ブラウザーが利用者の操作やsecure contextを求めることがある。対象のブラウザー・埋め込み先で確認する。
- URLのfragment等でリプレイを共有する場合は、長さの上限と公開範囲を確認する。

このルールは提供段階です。このHarness自体の検証としてUnity・Godot・ブラウザーのゲームでの運用は未実施であり、運用実績を保証しません。
