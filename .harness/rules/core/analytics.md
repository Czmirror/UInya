# Analytics

利用状況の計測（アクセス解析、イベント計測等）や、ゲームのプレイ記録を追加・変更する場合に適用します。
エラー・crashの報告は[Error reporting](error-reporting.md)で扱います。
目的は、開発中の操作を本番の数字に混ぜないこと、利用者の情報を計測サービスへ送らないこと、計測の失敗で本来の操作を壊さないこと、数字の意味を取り違えないことです。

既存ルールとの分担:

- 計測に出してはいけない秘密・個人情報の分類は[Sensitive data](sensitive-data.md)。
- 広告・アフィリエイトの表示、置き場所、本番以外で本番の広告を出さないことは[Monetization](monetization.md)。
- AIが計測サービスの管理画面や外部サイトを操作するときの承認は[Safety](safety.md)。
- 公開後でないと確かめられないことを未検証として残す考え方は[Runtime verification](runtime-verification.md)。
- ゲームのプレイの再現（リプレイ文字列・状態ハッシュ）は[Game replay](game-replay.md)、セーブデータは[Save data](save-data.md)。プレイ記録はどちらとも別物として扱う。

## Web・アプリ共通

### 送る環境と送る値

- 本番の測定IDへは本番だけが送る。ローカル・プレビュー・ステージング・testでは送らないか、別の測定IDにする。
- Webでは、本番かどうかをURLを解釈してscheme・host・pathで照合して決める。文字列の部分一致（`includes('example.com')`等）にしない。公開先のhostやpathを変えるときは、同じ変更で判定も更新する。URLを持たないアプリでは、ゲームと同じくリリースビルドかどうか等の、ビルド時に決まる値で判定する。
- 計測サービスの標準のページビューは、クエリ付きのURLやページタイトルを送ることがある。token・メールアドレス・招待コード・検索語などがURLやタイトルに入るページでは、送る前に取り除くか、そのページを計測しない。
- イベント名とパラメータは仕様で列挙し、許可リストにある値だけを送る。未知の値は送らない。
- 表示文言・自由入力・生のURL・利用者のIDそのものは送らない。利用者を区別する必要があるなら、[Sensitive data](sensitive-data.md)に従って仮名にする。
- 流入元のパラメータ（UTM等）は、外部の掲載先からのリンクだけに付け、内部リンクに付けない。値に個人を特定できる情報を入れない。

### 実装

- 送信処理は1か所（モジュール・service）に集め、画面やcomponentごとに書かない。後から描画される要素も同じ経路で計測できるようにする（例: 文書全体でのクリックの委譲）。
- 計測の読み込みや送信が失敗しても（広告ブロッカー、ネットワーク）、本来の操作を止めない・遅らせない。

### 測定の仕様

- 仕様書（[Workflow](workflow.md)の「仕様書」）に、目的 → 見る指標 → イベントの対応を書く。
- 指標の意味の限界を書く。例: 問い合わせボタンのクリックは問い合わせの成立ではない。ゲームの起動リンクのクリックは起動の成功ではない。
- いつ、どの程度の数がそろったら評価するかを書く。数が少ない間は、率の上下で良し悪しを決めない。

### 検証

- 単体testで、本番以外では本番の測定IDへ送らないこと（送らない方式なら初期化もしないこと）、許可外の値を送らないこと、送信が失敗しても操作が続くことを確かめる。
- 実際のブラウザで、ローカルでは計測のタグが読み込まれないことを確かめる。
- 公開後の実際の到着（計測サービスのリアルタイム表示・DebugView等）は公開前には確かめられない。完了報告とPRに未検証として書き、公開後に確かめる。

### 告知・同意と管理操作

- 計測を新しく入れる、送る内容を増やす、送り先を増やす場合は、告知（プライバシーポリシー、外部送信の説明）と同意（地域によるcookieの同意、Consent Mode等）の要否を、提案する仕様として計画に書き、人間が決める。
- 法令（日本の電気通信事業法の外部送信規律、GDPR等）の対象になるかどうかを、AIは断定しない。判断に必要な事実（何を、どこへ、いつ送るか）を整理して示す。
- 計測サービスの設定変更（カスタムディメンション、キーイベント、データ保持期間等）、Search Consoleの登録、外部サイトのプロフィール編集は、Safetyの承認が必要な外部操作として扱い、計画に「行う / 行わない」を書く。

## ゲームのプレイ記録

プレイテストで「どこで詰まったか」「どこでやめたか」を知るための記録です。
少人数のプレイテストでは口頭の感想だけでは分からないことが多く、難易度の調整に役立ちます。

- まず外部へ送らないローカルの記録から始める。1プレイごとに、build識別子、ステージ、開始・終了と結果、死亡の位置と原因、経過時間、リトライ回数をファイルへ書き出し、テスターから受け取って集計する。
- [Game replay](game-replay.md)を採用している導入先では、記録にリプレイ文字列か、再現に必要なseedとbuild識別子を含め、多くの人が詰まる場面を再現できるようにする。
- 記録はセーブデータとは別の場所・形式に置き、記録の失敗でセーブやゲームの進行を止めない。
- イベントは固定の名前と列挙値にする（例: `level_start`、結果が`clear`・`death`・`quit`の`level_end`、原因を列挙値で持つ`death`）。位置は区画に、時間は区間に丸める。毎フレームの記録・送信はしない。
- 公開版で外部の計測サービスへ送るのは、リリースビルドだけであること、告知があること、設定で止められること、の3つがそろってからにする。開発ビルドとエディタからは送らない。
- 計測サービスのサーバー向けAPIの秘密（例: GA4のMeasurement Protocolの`api_secret`）をゲームのビルドに入れない。配布したビルドからは誰でも取り出せる前提で扱い、必要ならサーバーを経由する。
- 埋め込みで配信する場合（unityroom等のiframe）は、ページ側に計測のタグを置けないことがある。配信先の規約やプライバシーの要件を確かめ、送るかどうかは人間が決める。
- 結果を読むときは、率より実数と個別のプレイ（リプレイ）を見る。

## 記録する場所

使う計測サービス、本番の判定方法、測定IDを送る環境、告知の場所、プレイ記録の置き場所は、ステアリング`.harness/steering/tech.md`の「計測」に要点だけを書きます。
ステアリングがない導入先では`AGENTS.md`に書きます。
