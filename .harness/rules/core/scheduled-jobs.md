# Scheduled jobs

バッチ処理・定期実行（cron、scheduler、Cron Triggers、GitHub Actionsの`schedule`など）を追加・変更する場合と、定期処理が動かない・二重に動くといった問題を調べる場合に適用します。
祝日・営業日・休業日で処理を変える場合（出荷日・納期・支払日・締め日の計算、休日には動かさない定期処理など）は、[祝日・営業日](#祝日営業日)の節を適用します。
CIの検査の定期実行（依存の脆弱性検査など）は[CI/CD](cicd.md)に従います。常駐するqueue workerの再試行・冪等性はstackのルール（例: [Laravel](../stacks/laravel.md)）に従います。

目的は、何が・いつ・どこで動くかをrepositoryを見れば分かる状態にし、SSHでサーバーに直接入れた出所の分からないcronが動き続けることや、サーバーの作り直し・一時的なサーバー・台数の増減での登録漏れ・二重登録を防ぐことです。

既存ルールとの分担:

- 実行の記録は[Logging](logging.md)、失敗の通知は[Error reporting](error-reporting.md)。
- 大量更新のtransaction・競合時の再試行は[Database](database.md)と[SQL](../stacks/sql.md)。
- スケジュール設定のdeployは[CI/CD](cicd.md)、本番での実行・停止の承認は[Safety](safety.md)。

## スケジュールの置き場所

- スケジュール（いつ・何を動かすか）は、repositoryで管理するコードか設定ファイルに書く。サーバーにSSHで入って`crontab -e`などで直接登録しない。AIもサーバーへ直接登録しない。
  例: Laravel scheduler（`routes/console.php`）、Cloudflare Workersの`wrangler.toml`の`[triggers] crons`、Vercelの`vercel.json`の`crons`、GitHub Actionsの`on.schedule`、KubernetesのCronJob、アプリ内のscheduler library。
- 起動するもの（トリガー）と、実行する処理（処理本体）を分ける。処理本体はコマンド・関数にし、トリガーなしでも手動で動かせるようにする（再実行・試験のため）。
- サーバー側に1行だけ必要な場合（例: Laravelの`* * * * * php artisan schedule:run`）は、その1行もprovisioningのコード（Dockerfile、IaC、Ansible、deploy script）に置く。
  それがないprojectでは、運用手順書と導入手順に書き、新しいサーバーで登録を確かめる手順を含める。
- 共有ホスティングなどでcrontabにしか書けない場合は、登録内容をrepositoryの文書に書き、サーバーの内容と食い違っていないかを確かめる手順を決める。
- 新しく外部のscheduler・serviceを導入する場合は、依存の追加として[Safety](safety.md)のASKに従う。

### repositoryにないcronを見つけたとき

- サーバーのcrontab・systemd timerなどに、repositoryに書かれていない定期処理を見つけたら、勝手に消したり書き換えたりせず、人間に報告する。
- 報告には、何が・いつ動いているか（分かる範囲）と、repositoryへ移す案を書く。移行は本番の変更なので、別の計画と承認で行う。
- 本番サーバーの中身を調べること自体も、[Safety](safety.md)のASKに従う。

## 多重実行と冪等性

- 複数のサーバー・コンテナ・一時的なサーバーで、同じ処理が同時に動かないようにする（例: Laravelの`onOneServer`、DB・cacheのlock、単一の専用worker）。
- 前回が終わる前に次が始まる場合の扱い（待つ・skipする・並行してよい）を決め、`withoutOverlapping`・lock・`concurrency`などで実装する。
  lockには期限を付け、異常終了で処理が止まったままにならないようにする。
- 同じ処理が2回動いても結果が壊れないようにする（処理済みの記録、一意制約、対象期間を引数で受ける）。
  メール・通知・決済など外部への送信は、二重送信を防ぐ仕組みを計画に書く。メールの送り方は[Email](email.md)に従う。
- 1回の実行にtimeoutを設ける。大量のデータは分割して処理し、途中で止まっても続きから再開できるようにする。

## 時刻と頻度

- 時刻帯（timezone）を明示する。Cloudflare Cron Triggers・GitHub Actions・Vercel CronはUTCで動く。アプリの時刻帯と違う場合は、コメントで日本時間などを併記する。
- 夏時間のある時刻帯では、切り替え日に処理が飛ぶ・2回動くことを考える。
- 処理対象の期間を、実行された時刻から推測するだけにしない。日付などを引数で受けられるようにし、遅れた実行や再実行で対象がずれないようにする。
- 環境・プランの制限（最短間隔、実行時間の上限、GitHub Actionsの遅延や間引き）を確かめ、要件に合わない場合は計画で人間に示す。

## 実行漏れと失敗の検知

- 開始・終了・処理件数・所要時間を記録する（[Logging](logging.md)）。失敗の通知は[Error reporting](error-reporting.md)に従う。
- 例外の通知だけでは「動かなかった」ことに気づけない。重要な定期処理には、決まった時刻までに成功の記録がなければ通知する仕組み（heartbeat、最終成功時刻の監視）を提案する。採用するか・通知先は人間が決める。
- GitHub Actionsの`schedule`は、公開repositoryで60日間活動がないと無効になる。止まると困る業務処理には使わないか、無効化に気づく手段を用意する。
- 実行漏れの後に追いつくか（まとめて処理する・skipする）を決めて書く。

## 環境ごとの扱い

- どの環境で動かすか（本番だけ、staging・previewでは止める、別のデータで動かす）を決める。
  previewや一時的な環境から、本番の宛先へメール・通知・外部への書き込みが出ないようにする。
- 開発では、手動実行かローカル用のscheduler（例: `php artisan schedule:work`）で確かめる。本番のスケジュールを手元から起動しない。
- 本番での手動実行、スケジュールの停止・変更、過去分の再実行は[Safety](safety.md)のASKとする。

## 検証と記録

- 処理本体はトリガーと切り離してtestする（対象期間、0件、大量、途中での失敗、2回の実行）。
- スケジュールの式は、可能なら一覧コマンド（例: `php artisan schedule:list`）や設定の検査で確かめ、完了報告に「次にいつ動くか」を書く。
- deploy後に、最初の実行が成功したかを確かめる手順を計画に含める。
- 定期処理の要点（どこに定義したか、何が起動するか、時刻帯、実行漏れの検知）は、ステアリング`.harness/steering/tech.md`の「定期実行」に書き、処理ごとの一覧や手順の詳細は運用手順書に置く。

## 祝日・営業日

祝日は毎年決まり直します（日本の春分の日・秋分の日は前年の2月に決まり、法改正で動くこともあります）。
作ったときに正しくても、更新しなければ翌年からずれます。また、データを更新したときに過去の判定や確定した結果が変わらないようにします。

### データの持ち方

- 祝日をコードに直接書かない。出典のあるデータ（日本なら内閣府の「国民の祝日」CSV）か、保守されているlibraryから取り込み、出典と取り込んだ日を記録する。libraryは[Libraries](libraries.md)に従って保守の状況を確かめて選ぶ。
- 振替休日・国民の休日を含めた、実際の祝日の一覧を正とする。計算式で求めるlibraryを使う場合は、特例の年（例: 2019年の即位の日、2020・2021年の祝日の移動）をtestで確かめる。
- 会社独自の休業日（年末年始・夏季休業など）は、祝日とは別の設定（DB・設定ファイル）に分ける。祝日データを入れ替えても消えないようにするため。
  管理画面で変える場合は[Admin screens](admin-screens.md)の変更の記録にも従う。
- 祝日の判定は、業務の時刻帯の日付で行う（日本ならAsia/Tokyo）。サーバーやDBの時刻帯（UTCが多い）の日付で判定しない。
- 複数の国を扱う場合は、国ごとに同じ考え方（出典、範囲の確認、過去を変えない）を当てはめる。
- 祝日に処理をするか（祝日に出荷するか、祝日を締め日にするか等）は業務の判断なので、AIが決めずに仕様として人間に確かめる。

### 更新漏れに気づく

- 祝日データが今日から一定期間先（例: 翌年の末まで）あるかを確かめるtestを書き、通常のCIに加えてCIの定期実行（月1回など、[CI/CD](cicd.md)）でも動かす。
  期間は、翌年の祝日がそろう時期（日本では例年2月）に合わせて決める。
- データの範囲外の日付で判定されたら、平日とみなさずエラーにするか通知する。黙って平日として扱わない。
- 毎年の更新作業（誰が・いつ・何を取り込むか）を運用手順書に書く。libraryの場合は、依存の更新（Dependabot等）を取り込む手順でよい。

### 過去の判定をずらさない

- データの更新は、新しい年の追加と誤りの修正だけにする。過去の年を消したり、まとめて置き換えたりしない。
- 更新で過去の年の内容が変わる場合（データ元の訂正など）は、変わった日付の一覧を人間に見せ、承認を受けてから取り込む。過去の年の祝日をtestに固定しておき、意図しない変化に気づけるようにする。
- 確定した結果（顧客に伝えた納期・支払日・期限、締めた集計）は、そのとき計算した日付を保存する。表示や再集計のたびに今の祝日データで計算し直さない。
- 会社の休業日を変えるときは適用開始日を付けて記録し、過去の日付に遡って効かせない。遡って直す必要がある場合は、影響する確定済みの結果を一覧にして人間が決める。
- 計算に使った祝日データの版を結果ごとに記録するかは、監査が必要なprojectだけ計画で決める。

参考: 内閣府「[国民の祝日について](https://www8.cao.go.jp/chosei/shukujitsu/gaiyou.html)」（祝日の一覧のCSVを公開している）。
