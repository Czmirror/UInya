# Display states

データを表示する画面（一覧・詳細・集計・グラフ・ダッシュボード、ゲームのランキングや記録の画面を含む）を作る・変える場合と、
Webのエラーページ（404・500等）・メンテナンス表示を作る・変える場合に適用します。
画面が真っ白になる、「undefined」が出る、エラー画面がおかしいといった問題を調べる場合にも読みます。

目的は、データがそろった状態だけを作って確かめた結果、初めて使うとき・データを消した後・項目が欠けたデータ・存在しないURLで、
画面が壊れる、内部の値や内部情報がそのまま出る、誤ったステータスコードを返す、といった事故を防ぐことです。
パート1は画面を持つすべてのprojectに、パート2はWebだけに適用します。

既存ルールとの分担:

- 例外の捕捉と開発者への報告は[Error reporting](error-reporting.md)。このルールは利用者への見せ方を扱う。
- 入力のnull・空・未指定の区別は[Input validation](input-validation.md)。このルールは表示する側を扱う。
- 入力欄のエラー表示、管理画面の空の一覧・エラーの文言、集計の定義は[Admin screens](admin-screens.md)。
- 機密・stack traceを応答に出さないことは[Security](security.md)と[Logging](logging.md)。
- 配信の設定・キャッシュは[Web delivery](web-delivery.md)。検索の観点での404は[Web](../stacks/web.md)の「検索・共有されるページ」。
- ゲームのセーブデータの保存・読込は[Save data](save-data.md)。見た目の水準と確認の報告は[UI visual](ui-visual.md)。

## パート1: データの状態

### 状態を分けて作る

- 画面や部品ごとに、読み込み中・データなし・エラー・データありの4つの見せ方を用意する。「データなし」と「読み込みに失敗した」を同じ表示にしない（失敗に気づけなくなるため）。
- 読み込みが終わるまで「データなし」を出さない。読み込み中の表示は、すぐ終わる場合にちらつかないようにする。
- 画面の一部（グラフ1つ、横のリスト1つ）の失敗で画面全体を真っ白にしない。失敗した部分だけにエラーを出し、ほかは表示する。
- 失敗の表示には、再読み込みなど次の操作を置く。内部情報（stack、SQL、内部ID）は出さない。

### データがないとき

- 「まだ登録がありません」だけで終わらせず、次に何をすればよいか（最初の1件を作るボタン、使い方の説明）を示す。
- そもそもデータがない場合と、検索・絞り込みの結果が0件の場合とで文言を分ける。0件のときは、条件を外す操作か条件を見直す案内を出す。
- 初めて使う人の画面（初期データがない、設定が未完了）を、仕様書の画面一覧に1つの状態として書く。
- APIが一覧を返すとき、0件は空の一覧（`[]`）と成功のステータスで返し、404やnullにしない（画面側で失敗と0件を区別できるように）。

### 値が欠けている・nullのとき

- `null`・`undefined`・`NaN`・`Invalid Date`や、空のまま詰まった欄をそのまま画面に出さない。
- 値がないときの表示（例: 「-」「未設定」「未入力」）はprojectが仕様で決める。決まっていなければAIは「-」を使い、
  [Workflow](workflow.md)の「仮の調整値」として計画と完了報告に挙げる。
- 値がないときの表示を作る処理を1か所にまとめ、全画面で使う。画面ごとに書き分けない。
- 0と「値がない」を区別する。0円・0件は「0」と出し、値がないものは決めた表示にする。
- 「値がない」の意味が複数ありうる場合（未入力・非公開・取得失敗・対象外）は、区別するかを仕様で決める。AIが意味を推測で決めない。
- 画像・アイコンがない、または読み込めないときの代わりの表示（初期アイコン等）を用意する。

### 参照先が消えたとき

- 削除・退会・非公開になったものを参照している行は、落ちずに「削除済みのユーザー」などと表示する。リンクは張らないか、消えた旨を示すページへ送る。
- 消えたときに何を残すか（名前を残す、匿名にする）は、[Sensitive data](sensitive-data.md)と合わせて仕様で決める。

### 集計・グラフ

- 0件のとき、平均・割合が0除算で`NaN`・`Infinity`にならないようにし、決めた表示にする。
- グラフは0件・1件でも崩れないこと（軸、凡例、空のときの文言）を確かめる。

### ゲーム

- 初めての起動（セーブデータなし）、ランキングが0件、通信が必要な機能の失敗（オンラインのランキングが取れない等）で、落ちずに表示できることを確かめる。

### 確かめ方

- 次のデータで実際の画面を開いて確かめる。testだけで済ませない。
  - 空のデータベース、または初めての利用者
  - 任意の項目が欠けたデータ、古い形式のデータ
  - 参照先を削除したデータ
  - 読み込みの失敗と遅延（通信を止める・遅くする）
- 自動のtestでは、0件・1件・値の欠け・読み込みの失敗の表示を確かめる。部品ごとに画面を確かめる仕組み（Storybook等）があれば、4つの状態をそれぞれ登録する。
- 完了報告に、確かめた状態の一覧を書く。可能ならスクリーンショットを添える。

## パート2: Webのエラーページ

### ステータスコード

- 見つからない: 404（消したことが明らかで戻らないなら410も可）。権限がない: 403。ログインが必要: ログイン画面へ送るか401。serverの失敗: 500。メンテナンス中: 503。
- 「見つかりません」の画面を200で返さない（ソフト404。検索に不要なページとして登録され、監視でも失敗に気づけない）。
- ブラウザの中で画面を切り替える作り（SPA）では、存在しないURLをserverや配信の設定でも404にする。できない場合は検索に出ない設定（`noindex`）にし、理由を計画に書く。
- メンテナンス中は503と`Retry-After` headerを返す（検索エンジンにページが消えたと扱わせないため）。
- APIは、HTMLのエラーページではなく、決めた形のJSONとステータスコードを返す。

### 内部情報を出さない

- 本番では、stack trace、SQL、ファイルのpath、frameworkやserverのversionを表示しない。
- frameworkのデバッグ表示が本番で切れていることを、設定の値で確かめる（例: Laravelの`APP_DEBUG=false`、Djangoの`DEBUG = False`、Expressの`NODE_ENV=production`）。設定名は実装時に対象versionの公式文書で確かめる。
- 問い合わせに使うエラーの番号（ログと結びつく識別子）は表示してよい。個人情報や内部の値を含めない。

### 次の行動を示す

- 何が起きたかを平易な言葉で書き、次の行動（トップへ戻る、検索、前のページ、時間をおいて再試行、問い合わせ先）を置く。利用者の操作のせいだと決めつける文言にしない。
- サイトの見た目（header、色、文字）とそろえる。frameworkの既定の画面のままにしない。

### 存在を知られたくないもの

- 他人のデータや非公開のものなど、存在を知られたくないものに権限なしでアクセスされたときは、403ではなく404を返す（IDを順に試して存在を探られないように）。
- 存在は知られてよく、操作の権限だけがない場合（ログイン済みの利用者が管理機能を開いた等）は403を返す。
- どのURLがどちらに当たるかを仕様書に書く。どちらの場合も、server側で毎回認可する（[Security](security.md)）。

### 500ページとメンテナンスページ

- DB・ログインの状態・外部サービスに頼らず表示できるよう、なるべく静的なHTMLで作る（DBが落ちたときに500ページも出せなくなるため）。
- アプリが落ちたときにWebサーバー・CDN・hosting側が出すエラーページも、同じ見た目にできるかを確かめる。できない場合は既定のままでよく、その旨を計画に書く。

### キャッシュ

- 500・503を配信の仕組みに長く覚えさせない。404を覚えさせる時間も短くする（一時的なエラーが直った後も出続けないように）。

### 記録と通知

- 500は[Error reporting](error-reporting.md)に従って報告する。
- 404は1件ずつ通知しない（botの探索で大量に来るため）。件数の急な増加と、サイト内のリンク切れを見られるようにする。

### 確かめ方

- 存在しないURLを開き、画面とステータスコードの両方を確かめる（例: `curl -I`、ブラウザの開発ツール）。
- 本番と同じ設定のbuild（本番相当の環境）でわざと500を起こし、内部情報が出ないこと、見た目がそろっていることを確かめる。本番そのもので起こさない。
- メンテナンス表示があれば、503と`Retry-After`が返ることを確かめる。
