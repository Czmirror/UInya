# Runtime verification

stackのルールが実動検証を求める環境で、実行時の挙動を変更する作業に適用します。
現在の対象は[Unity](../stacks/unity.md)と[Godot](../stacks/godot.md)です。導入先は`AGENTS.md`またはステアリングで対象のstackを追加できます。
目的は、コンパイルやheadlessの成功を「実際に動いた・表示された」ことの代わりにしないことです。
エンジン固有の起動方法・Editorの扱い・出力先の確認は、各stackのルールに書きます。

## 計画と完了条件

実行時の挙動を変更する作業では、変更した機能を実際の対象scene・画面で動かす検証を必須とします。
計画・試験仕様書には対象scene・画面、起動経路、入力・状態遷移、期待する挙動、検証手段を示します。
移動・演出・camera・UI・文字表示などの変更は、描画と必要な操作を伴う確認で期待する動きと照合します。
効果音・BGMなど音声の変更は、対象の場面で再生されることと、再生に関するerror・warningがないことを確認します。
セーブデータの保存・読込の変更は、保存 → 終了 → 再起動 → 読込で値が戻ることを確認します（[Save data](save-data.md)）。
表示なしのリプレイ・botによる確認は隔離したtestに当たり、実際のscene・画面での確認を代替しません（[Game replay](game-replay.md)）。
文書・コメントだけの変更など、実行時に影響しない作業は理由付きで適用外にできます。
全stageの通しプレイや全platform buildを毎回必須にはせず、影響範囲から検証対象を選びます。

## 検証の区別

次の検証は目的と結果を区別してください。

- コンパイル・構文検査・import: 変更したコードと素材の読み込みでerror・warningがないことを確認する。
- 隔離したtest: 対象ロジックやcomponentの条件を確認する。
- 実際のscene・画面での実行: 実際の起動経路、参照、lifecycle、状態遷移を含めて変更機能を確認する。
- 描画・操作: 見た目や入力に関する期待結果と、画面上の挙動を照合する。確かめる入力デバイスの範囲は[Controls](controls.md)で決める。
- 音声: 対象の操作・状態で音声が再生されることを、再生の記録・出力・人間の報告などで確認する。聞こえ方・音量の好みは含めない。
- 対象platformの出力とその実行: platform固有の変更・問題に必要な範囲を確認する（例: Web export、埋め込み先）。Webへの出力では、配信先のheader・キャッシュも結果に関わる（[Web delivery](web-delivery.md)）。

数式・隔離test・コンパイル・buildの成功だけで、実際のscene・画面での確認を代替しません。
headlessの結果だけでは、観察していない描画・音声・入力・platform固有動作を確認済みにしません。

## 実行環境の安全な利用と実行不能時の対応

Editorや実行中のアプリがある場合は、既存sessionを安全に利用できる操作手段やproject提供の検証経路を先に確認します。
未保存の作業を保護し、検証のためにEditorを強制終了したり、無断で保存・破棄したり、lock fileを削除したりしません。
操作toolの不足を理由に、package・pluginの導入や設定変更を無断で行いません。

画面lock、操作tool不足、表示環境がない、license、起動競合などで実行できない場合は、安全な代替経路を調べます。
解決できなければ、具体的な障害と必要な解除操作、または人間が実施できる検証手順・期待結果・必要な証拠を提示します。
単に「実動は未確認」と報告して作業を完了扱いにせず、必須検証が残る間は[Workflow](workflow.md)のBlockedとして残件を示します。
レビュー用差分やdraft PRの共有はできますが、完了・マージ可能と表現しません。

### 実動確認待ちのPR

必須検証が残る変更をPRで共有する場合は、次のように進めます。

1. PRはdraftのまま出し、タイトルの先頭に「[実動確認待ち]」を付ける。本文でマージ可能と書かない。
2. PR本文の「人が確認すること」に、人が実施する確認手順を5手順以内で書く。手順には次を含める。
   - 起動する場面。
   - 操作。
   - 期待する結果。
   - 見るべき表示・ログ（error・warningの出力先）。

   エンジンやEditorに詳しくない人でも、その手順だけで実施できる書き方にする（[Writing for humans](writing.md)）。
3. 人の確認結果を受け取ったら、報告の出典と確認できた範囲をPR本文に記録する。期待と違う結果なら、Implementへ戻る。
4. タイトルの印を外すこととdraftの解除は、PRの状態を変える外部への書き込みである。人間が行うか、人間の操作承認を得てからAIが行う。
5. 確認結果を受け取る前に、AIがマージ・draft解除をしない。

## 人間確認との関係

[UI visual](ui-visual.md)や[Assets](assets.md)の「人間確認として報告」は、このルールの必須検証を緩めません。
このルールの対象に当たる作業では、必須検証が残る間はBlockedとし、人間に実施を依頼する場合もその結果を受け取るまで完了にしません。
対象外の作業や、必須検証を終えたうえで残る好み・品質の判断（見た目の印象、音の聞こえ方・音量など）は、従来どおり人間確認として報告します。

## 記録する証拠

エンジン・runtimeのversion、対象revisionと未commit差分、対象scene・画面、実施手順・期待結果、実施者・手段、実際の結果を記録します。
error・warningの出力と既存問題の区別、ログ・画像・動画などの証拠への参照、未検証範囲も示します。
証拠には機密情報を含めず、描画や操作を確認できる証拠と、ログだけの証拠を区別します。
人間が実施した場合はその報告の出典と確認範囲を残し、AI自身が実行・観察した結果として扱いません。
検証後に変更した場合は、影響する確認を再実行します。

このルールは提供段階です。このHarness自体の検証としてUnity Editor・Godotでの運用は未実施であり、運用実績を保証しません。
