# Design and dependency boundaries

設計・責務の配置・module間依存を変更する計画で適用します。
Clean Architecture等の原則を判断基準に使い、固定の層数・directory名・class構成を強制しません。
目的は、仕様変更の影響範囲を抑え、重要なロジックを理解・検証しやすくすることです。
SOLID・DRY・YAGNI等の適用判断は[共通コーディング原則](principles.md)に従います。

## 共通の判断基準

- 既存の構成とFrameworkの責務分担を先に調査し、無関係な再構成を行わない。
- 業務上の判断と、UI・DB・HTTP・filesystem等の外部I/Oを区別する。
- 複雑な業務ロジックは、外部環境を起動しなくても主要な分岐をtestできる形を優先する。
- 採用したmodule境界と依存方向を守り、循環依存や内部実装の直接参照を増やさない。
- interface / trait / callback等は、I/Oの置換・test・変更点の隔離など具体的な理由で導入する。
- 安全性やtransaction、整合性を損なってまで、機械的な責務分割を優先しない。

## Clean Architectureを選ぶ場合

業務ルールを内側、UI・DB等の詳細を外側に置き、source codeの依存を内側へ向けます。
内側から保存等が必要なら、内側が必要とする小さな契約を定義し、外側が実装します。
実行時の呼び出し方向と、sourceのimport依存方向は区別してください。
外側の組立箇所で具体実装を接続し、業務ルールにFramework・ORM固有型を漏らさない設計を検討します。

たとえば料金計算では、税率・割引条件を入力に受けて計算する処理と、DBから条件を取得する処理を
分けると、DBなしで計算の境界値をtestできます。これだけで足りるなら専用の層やinterfaceは不要です。

## 採用の深さ

| 状況 | 初期判断 |
| --- | --- |
| 小さなscript・静的UI・単純なCRUD | 既存の慣習と素直なmodule分割を優先 |
| 複雑な業務判断、複数の入口や外部I/O、長期的な変更が多い | 業務ロジックとadapterの境界を明示する案を検討 |
| 既に層・module境界が定義されている | 既存の契約を維持し、変更理由を計画に示す |

実装のないinterface、転送するだけの層、根拠のない汎用Repository、不要なDTO変換を増やしません。
仮想的な将来の差し替えだけを理由に抽象化せず、具体的な変更・test上の利点と保守コストを比較します。
既存のORMやFrameworkを排除すること自体を目的にしません。

## 図で示す設計

文章だけでは抜けや矛盾に気づきにくい設計は、Markdown内のMermaidで図にします。
図は理解とレビューを助ける補助であり、すべての計画に必須ではありません。

描く条件（いずれかに当てはまる場合）:

- 状態が3つ以上ある、または戻る・取り消す・再試行する遷移がある。
- 複数のcomponent、外部I/O、非同期処理をまたぐ処理の流れを変更する。
- DBのテーブル・関連を追加・変更する。
- [Security](security.md)で特定する信頼境界がある。

| 対象 | 図の種類 |
| --- | --- |
| 状態遷移 | `stateDiagram-v2` |
| 処理の流れ・呼び出し順 | `sequenceDiagram` |
| テーブルと関連 | `erDiagram` |
| 信頼境界・データの流れ | `flowchart` |

- 1つの図には1つの関心事だけを描き、全体図を一枚に詰め込まない。
- 状態遷移図の各遷移は、禁止する遷移も含めて受け入れ条件とtestに結び付ける。図の遷移にtestがない場合は、その理由を計画に書く。
  最終レビューでは[Review](../../templates/review.md)と観点ファイル[Data](../../templates/review/data.md)に沿って、遷移ごとに対応するtestを照合する。
- 図と文章・表が食い違った場合は、承認済みの計画の文章・表を正とする。仕様を変えたら、図も同じ変更で更新する。
- 条件に当てはまらない小変更では図を描かない。中身のない図で計画を水増ししない。
- このHarnessにはMermaidの構文検査は含まれない。描画結果はPR等の表示で確認する。

## 計画・レビュー・CI

計画には、必要な範囲で「責務」「許可する依存方向」「外部I/O」「test方法」「分けない理由」も記録します。
構成の大幅変更は人間の計画承認を受け、機能変更と無関係な移行を混ぜません。
レビューではdirectory名ではなく、実際の依存・責務・変更時の影響を確認します。

境界が確定したprojectでは、既存のimport制限、package / crate境界、循環依存検査等をCIへ組み込めます。
必要なboundary checkはProject Profileの`lint`または`test`に必須項目として追加します。
新しいtoolの追加はSafetyに従います。このHarnessには言語横断のarchitecture検証器は含まれません。
CIは設定された依存違反を検出できますが、責務分割の妥当性や過剰な抽象化は人間とAIのレビューに残ります。
