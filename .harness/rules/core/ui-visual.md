# UI visual

画面・UIの見た目を作る・整える場合と、画面を新しく作る・画面の部品や流れを変える計画を立てる場合に適用します。
プロトタイプ、Web、ゲームのUI、デスクトップアプリを含みます。
目的は、毎回の指示がなくても見た目の水準をそろえ、デザインツールの成果物を安全に取り込み、画面の形のずれを作る前に見つけることです。
特定のデザインツールの使用は求めません。使うツールは導入先の`AGENTS.md`が決めます。

## 見た目の水準

計画に、次の水準を1つ書きます。

| 水準 | 用途 | 見た目の扱い |
| --- | --- | --- |
| A 動作確認用 | 動きや処理だけを確かめる | 整えない。既存のstyleを壊さないことだけ確認する |
| B 共有・デモ用 | 人に見せる、方向性を相談する | 下の「水準Bの最低限」を満たす |
| C 利用者テスト用 | 実際の利用に近い形で試してもらう | Bに加え、実際の文言・データ量・端末で崩れないことを確かめる |

人間の指定がなければBとし、計画に「既定のBを採用」と書きます。

水準Cでは、デモ用のきれいなデータだけでなく「最悪のデータ」でも崩れないことを確かめます。
長い名前・長いメールアドレス・1文字の名前・1件（単数と複数の言い分け）・大量の件数・大きな数字・絵文字・画像がない場合を、1つの試験用データに入れます。
値はでたらめな文字列にせず、DBの列の長さや入力の上限から決めます。文字を省略する（…）か折り返すかは項目ごとに決め、数字は省略しません。
0件・読み込み失敗の表示は[Display states](display-states.md)に従います。

## 水準Bの最低限

ツールを使わなくても満たせる内容です。

- 既存のdesign system・theme・UI libraryがあれば、それを優先して使う。新しく作らない。
- 色・余白・文字サイズ・角丸を1か所（CSS変数、theme、定数など）にまとめ、画面ごとに値を直書きしない。
- 余白と文字サイズは少数の段階（例: 4の倍数）から選ぶ。色は役割（背景・文字・強調・警告など）で名前を付ける。
- 承認済みの仕様やデザインがなくAIが選んだ値は、[Workflow](workflow.md)の「仮の調整値」として計画と完了報告に一覧で示す。
  人間が指定した値や、人間が採用を決めたデザインファイルの値は承認済みの仕様として扱い、指示なく変えない。
- contrast・focus表示・狭い画面の確認は、Webなら[Web](../stacks/web.md)、他のUIはその製品の方法で行う。

## デザインツール

- 使うツールは、導入先のステアリング`.harness/steering/tech.md`（ない場合は`AGENTS.md`の「Project固有ルール」）で指定する。
- 指定がなければ、AIはツールを使わず「水準Bの最低限」の方法で整える。ツールが役に立ちそうな場合は提案にとどめる。
- ツールの成果物は、種類ごとに次のように扱う。

| 成果物 | 扱い |
| --- | --- |
| デザインファイル・モック・スクリーンショット | 外観の参考にとどめ、commitしない（[Assets](assets.md)の参考画像と同じ）。AIが描く画面の設計図のHTMLは下の「画面の設計図」に従う |
| 書き出した画像・アイコン・フォント | 素材として[Assets](assets.md)に従い、入手元と利用条件を記録する |
| 色・余白・文字などの値 | 「水準Bの最低限」の1か所へ転記し、出典（ファイル名・ページ名）を記録する |

- 共有URLが署名付き、またはアクセス権の付いたものなら、記録やコードに残さない（[Sensitive data](sensitive-data.md)）。
- connector・MCP等でツール上のデザインを作る・書き換える操作は、外部サービスとアカウントの利用として[Safety](safety.md)に従う。

## 画面の設計図

画面の部品の並び、押す前の確認、データがないときの表示といった「画面の形」のずれは、文章の計画では読み流されやすく、
できあがった画面を見て初めて気づくと作り直しになります。そこで、作る前に番号付きの注釈を付けた設計図を1枚見せ、
完成後に実際の画面と並べて比べます。

### いつ作るか

- 作る: 新しい画面を作るとき、既存の画面に部品や手順を足す・並びを変えるとき、画面の流れ（どのボタンでどの画面へ進むか）を変えるとき。
  Web・アプリ・管理画面のほか、ゲームのタイトル・メニュー・結果画面・HUD（ゲーム中に重ねて出す体力や得点の表示）も含む。
- 作らない: 文言・色・余白だけの調整、不具合を元の形に直すだけの修正、[Workflow](workflow.md)の「小変更」。
  ゲームの手触り（速度・判定）のように、止めた絵では確かめられないもの。（設計図を作ること自体が目的にならないように）
- 迷う場合は、作るかどうかを計画の中で一行提案し、人間に任せる。

### 何を描くか

- 絵: 部品の配置を線と箱で描く。色や飾りは描かない（見た目は上の「見た目の水準」で別に決める）。
  文字はそれらしい仮のデータにし、長い名前や大きな数字も1つ入れる。本物の個人情報は使わない（[Sensitive data](sensitive-data.md)）。
- 番号付きの注釈: 部品ごとに番号を振り、「何のための部品か」「押すと何が起きるか」「守る条件（上限・下限、権限）」を1〜2行で書く。
  仕様書の受け入れ条件のID（AC1など）があれば添える。
- データあり以外の表示: 読み込み中・データなし・エラーを小さな枠で同じ1枚に添える（[Display states](display-states.md)）。
  取り消せない操作があれば、その確認の表示も添える（[Admin screens](admin-screens.md)）。
- 狭い画面: スマートフォンでも使う画面なら、狭い幅での並び方を小さく1つ添える。
- 1枚に1画面とする。複数の画面にまたがる流れは画面ごとに1枚にし、画面の移り変わりは[Design](design.md)の状態遷移図で示す。
- AIが決めた見た目・操作感の値（ボタンの文言、表示の順番、演出の時間など）は注釈で「仮」と書き、[Workflow](workflow.md)の「仮の調整値」に挙げる。
  入力の上限・下限、送信件数、保存期間、権限など業務・データ・securityに関わる値は仮の調整値にせず、
  Workflowの「提案する仕様」として選択肢・影響・推奨案を計画に示し、注釈には「要確認」と書く。

### 作り方と置き場所

- 既定は、外部の文字・画像・scriptを読み込まない1つのHTMLファイルで描き、ブラウザでPNG画像にして人間に見せる。
- ブラウザで画像にできない環境では、計画の中に文字で描いた図（罫線の箱）と注釈の一覧で代える。
- 導入先が上の「デザインツール」を指定していれば、そのツールで描いてもよい。その場合も注釈の一覧は計画の文章に書く。
- 注釈の一覧（番号と説明の文章）は計画に書き、絵の元のHTMLは計画と同じ`docs/work/<task-id>/`に置いてcommitする。
  PNG画像はcommitせず、見せるときに作る。

### 承認

- 設計図は計画と一緒に見せ、承認は計画と1回にまとめる。設計図だけ別に承認を求めない。
- 承認の対象は計画に書いた注釈の一覧と、それに対応する絵である。絵と注釈の文章が食い違ったら注釈の文章を正とし、絵を作り直す。
- 人間が設計図に直しを入れたら、直した設計図をもう一度見せる。番号は振り直さず、消した番号は欠番にする（完成後の比較で番号がずれないように）。

### 完成後の比較

- 完成したら、実際の画面のスクリーンショットを設計図と並べ、番号ごとに「設計どおり / 違う（理由）」を完了報告に書く。
- 違う点は設計図を黙って書き換えず、直すか、違ったままにする理由を書いて人間に判断してもらう。
- この比較は画面の形の確認であり、実際に動かして確かめること（[Runtime verification](runtime-verification.md)、下の「確認と報告」）の代わりにしない。

## 見た目の案を複数出す

見た目の方向が決まっていない新しい画面では、案を2〜3つ出して人間に選んでもらうと、作り直しが減ります。
ただし画像の案からは色・文字サイズ・余白の値が残らないため、実装のときにAIが目分量で値を決め、案と少しずつずれます。次のように出します。

- 出す場面: 新しい画面で、既存のdesign systemがなく見た目の方向が決まっていないとき。既存のdesign systemがあれば、それに沿った1案でよい。
- 違いの軸: 案ごとに「何を重視したか」を一言で書く（例: 信頼感／親しみやすさ／情報量）。色違いだけの案にしない（選ぶ意味がなくなるため）。
- 値の一覧: 画像と一緒に、色（役割名と値）・フォント・文字サイズ・余白・角丸の一覧を文字で出す。採用した案の一覧を「水準Bの最低限」の1か所へ転記し、出典を記録する。
  画像から読み取っただけの値は、人間が採用した案でも[Workflow](workflow.md)の「仮の調整値」とする。
- 中身: 文言とデータは仕様や既存の内容を使う。ない文言は案の中で「仮」と書き、実在しない機能・実績・数字を描かない。
- 画面の形: 画面の設計図があれば、その配置に合わせて描く。配置を変えた案は、変えた点を書く。食い違えば設計図の注釈を正とする。
- 素材: 案の中の写真・イラストを本番に使う場合は、[Assets](assets.md)に従って入手元と利用条件を確かめる。
- 記録: 選んだ案と理由を計画に1行残す。案の画像は上の「デザインツール」の表どおりcommitしない。
- 案を作るツールは「デザインツール」と同じく導入先が決める。

## 推奨ツール（参考）

どれを使うかは導入先が決めます。この表は選ぶときの参考で、使用を義務付けません。

| 用途 | 推奨 | 理由・注意 |
| --- | --- | --- |
| 画面・componentの設計、色や余白の値の受け渡し | Figma | 画面単位の設計と値の参照に向く |
| OGP・バナー・アイコンなどの画像、手早い見た目の案 | Canva | 素早く画像を作れる。Canvaの写真・イラスト等の利用条件は[Assets](assets.md)に沿って確認する |
| 外部SaaSを使えない、自分たちで運用したい | Penpot | OSSでself-hostできる |
| 小さなプロトタイプ | ツールなし | 「水準Bの最低限」だけで足りることが多い |

ツールの機能や価格は変わるため、この表には用途だけを書きます。

## 確認と報告

- 見た目は自動検証とは別に、人間確認として完了報告に書く。可能なら主要画面のスクリーンショット（広い画面・狭い画面）を添える。
  Unity・Godotなど[Runtime verification](runtime-verification.md)の対象では、その必須検証を先に済ませ、未実施ならBlockedとする。
- PDFを出力する機能では、画面ではなく出力したPDFをページごとに画像にして確かめる（[PDF output](pdf-output.md)）。
- デザインファイルと実装が食い違った場合は、承認済みの計画を正とし、差分を報告する。
- 画面の設計図を作った場合は、上の「完成後の比較」の結果も書く。
- 見た目の案から選んで作った場合は、選んだ案の値の一覧と実装の値の差を書く。
