# Performance

描画・更新処理・読み込み・素材・依存を変えて、フレーム時間・読み込み時間・メモリ・配信サイズに影響しうる場合に適用します。
遅い・重い・カクつくという相談を調べる場合と、性能の目標を決める場合にも読みます。
目的は、推測で最適化しないことと、測っていない性能を「問題ない」と報告しないことです。
エンジン固有の測り方は、各stackのルールに書きます。

既存ルールとの分担:

- 素材を加工するかの判断（頂点数・解像度などを数値で示して人間が選ぶ）は[Assets](assets.md)。
- 配信サイズに関わる圧縮・キャッシュは[Web delivery](web-delivery.md)。
- サーバーの処理・DBの問い合わせの性能（N+1、一覧の上限、index）は[Server performance](server-performance.md)。
- 新しいcheck・toolの追加の承認は[Safety](safety.md)と[Quality](quality.md)。

## 目標

- 目標のfpsと1フレームの時間（例: 60fpsなら約16.7ms）、対象の最低端末、Webの初回読み込みのサイズと時間を決める。Webサイトでは、必要ならCore Web Vitals（LCP・INP・CLS）も使う。
- 数値は人間が決める。根拠がないまま置く値は、確定していない仮の値として、[Workflow](workflow.md)の仮の調整値と同じく計画と完了報告に「仮」と明記して一覧にする。対象の端末の選択は利用者に関わる判断なので、AIの案は提案する仕様として示す。
- 決めた目標は、ステアリング`.harness/steering/tech.md`の「性能の目標」に書く。ステアリングがない導入先では`AGENTS.md`に書く。未定なら「未定」と書き、目標があるかのように報告しない。

## 測ってから直す

- 変更の前後をprofilerで測る。どこが遅いかを測らずに最適化を始めない。
- 測った条件を一緒に記録する: 端末・OS、ブラウザー、build種類（開発・製品）、解像度、場面、測った時間。
- 例: Godotのプロファイラ・Monitors、UnityのProfiler・Frame Debugger、ChromeのPerformanceパネル・Lighthouse。
- エディタ上や開発ビルドの数値を、製品版の性能として報告しない。開発ビルドで測った場合はそう書く。
- 平均だけでなく、引っかかり（一瞬だけ長いフレーム）も見る。カクつきは平均fpsに表れにくい。

## 確認する原因の例

- 毎フレームのメモリ確保と、それによるGC（使わなくなったメモリの回収処理）。
- 毎フレームのnode・objectの検索（名前・型での検索）。
- 大量の生成と破棄。必要ならobject poolを検討する。
- draw callの数と、重ね描き（同じ画素を何度も描くこと）。
- 物理のtick数、当たり判定の対象数。
- 圧縮していない大きな素材、必要以上の解像度。
- 読み込みを同期処理で行うことによる停止。

Webでは次も確認します。

- JavaScriptの配信サイズと、描画を止める読み込み（`<head>`の同期script等）。
- 画像の形式とサイズ、表示サイズとの差。
- 日本語フォントのサイズ。必要な文字に絞ったsubsetを検討する（Godot等は[Godot](../stacks/godot.md)のフォントの節と両立させる）。

## メモリ

長いプレイや、場面の切り替えを繰り返したときに、メモリが増え続けないことを確かめます。
切り替えの前後でメモリの量を比べ、増え続ける場合は解放されないobject・event listener・素材を探します。

## 回帰を防ぐ

配信サイズや読み込み時間の上限をcheckにするかを、計画で提案できます。
新しいcheck・toolの追加は承認対象です。上限の値は人間が決め、決めるまでは上の「目標」と同じく仮の値として示します。

## 報告

- 性能が良くなった・問題ないと書くときは、測った数値と条件を付ける。数値のない「軽くなった」「問題ない」は書かない。
- 対象の端末・ブラウザーで測れない場合は、未検証として残す。開発端末で測った結果を、対象の最低端末の結果の代わりにしない。
- 目標に届かない場合は、測った値・目標・考えられる対策と影響を示し、どうするかは人間が決める。
