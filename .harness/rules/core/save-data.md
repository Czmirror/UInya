# Save data

ゲームのセーブデータ（進行状況・設定・解放要素など、終了後も残して次の起動で読む値）を扱うprojectに適用します。
現在の対象は[Unity](../stacks/unity.md)と[Godot](../stacks/godot.md)です。導入先は`AGENTS.md`またはステアリングで対象のstackを追加できます。
目的は、保存の仕組みを確かめないまま実装を始めて、既存のセーブデータを読めなくしたり、壊したり、上書きしたりしないことです。
エンジン固有の保存先・APIの注意は、各stackのルールに書きます。

既存ルールとの分担:

- 読み込んだセーブデータの検証（信頼境界、読込時に適用する条件）は[Input validation](input-validation.md)。
- 秘密・個人情報・決済情報を含む場合の置き場所は[Sensitive data](sensitive-data.md)。
- 保存・読込の流れや状態を図で示す条件は[Design boundaries](design.md)。
- 保存形式の変更をCHANGELOGに書くことは[Release](release.md)。

## 初回確認

対象のstackで作業を始めるとき、ステアリング`.harness/steering/tech.md`の「データ保存」を確認します。
ステアリングがない導入先では`AGENTS.md`の同じ項目を確認します。

記録がない、または記録とコードの実態が食い違う場合は、その作業の計画に次を含めて人間に確認します。

1. コード・設定を検索して調べた現状（保存・読込している箇所、保存先、形式、versionの有無）。事実と推測を分ける。
2. 下の「確認項目」のうち、現状から決まらない点と、選択肢・推奨案。
3. 回答をステアリングへ記録する案。ステアリングには要点だけを書き、詳細は別の文書に置いて場所を示す。

回答を得るまで、保存・読込に触れる実装は始めません（[Workflow](workflow.md)のAwaitPlanApproval）。
保存に触れない作業は進めてよいですが、確認事項は報告の残件として示し続けます。
保存を使わないprojectでは、そのことを記録すれば足ります。

## 確認項目

- 保存する内容: 進行状況、設定（音量・キー割り当て等）、解放要素、課金・実績などの区分と、保存しないもの。
- 保存先とplatform: ローカルファイル、エンジンの保存API、Web出力時の保存領域、cloud保存やplatformのsave機能の有無。
- 形式: JSON・バイナリ・エンジン固有の形式など。読み込むと任意のコード実行やobjectの生成につながる形式は、外部から差し替えられうるデータに使わない。
- 書き込みのタイミングと安全性: 自動保存の契機、書き込み中の終了・電源断で壊れない方法（一時ファイルへ書いて置き換える、backupを残す等）。
- versionと移行: 形式のversionの持ち方、古い形式の移行方針、読めない・壊れたデータを見つけたときの挙動（初期化する前に退避する等）。
- slotと端末: 複数slot、複数端末やcloud同期での競合の扱い。
- 改ざんへの方針: 対策をするかどうかは人間が決める。

## 保存に触れる作業

保存する項目・形式・保存先・読込の流れを変える作業では、計画に次を示します。

- 既存のセーブデータとの互換: 変更前の形式を読めるか、versionの更新、移行の手順、移行できない場合の挙動。
- 読込のtest: 保存して読み戻すと値が戻ること、壊れたデータ・欠けた項目の扱いを確認する。
- 移行のtest: 利用者の手元に変更前の形式が残りうる場合（公開・配布済みの版がある場合）は、その形式のセーブデータを用意して読込と移行を確認する。初めて保存を作る場合は不要。
- 実動検証: [Runtime verification](runtime-verification.md)の対象なら、実際の起動経路で保存 → 終了 → 再起動 → 読込を行い、値が戻ることを確認する。
  Web出力が対象なら、ブラウザーの再読込後にも残ることを、出力先と埋め込み先で確認する。

形式・保存先の変更は、利用者の既存データに影響する重要仕様です。承認された計画にない変更を実装中に加えず、Planへ戻ります。

## 開発・検証時のデータ保護

検証のために、利用者や開発者の手元にある実際のセーブデータを上書き・削除しません。
検証は、本物と分けた保存先（test用のuser data directory、複製したprofile等）で行います。退避して戻す方法は、分けた上での追加の備えとして使い、分ける代わりにしません。
分けられない環境では、対象と手順を示して人間の承認を得ます。
本物のセーブデータを、testのfixtureやissue・PRへそのまま入れません。必要なら値を作り直します（[Sensitive data](sensitive-data.md)）。
