# Assets

画像・音声・フォント・3Dモデル・動画など、コード以外の素材と静的ファイルを追加・変更・移動する場合に適用します。
素材の利用条件は配布や公開の可否に関わるため、入手した経緯を後から確かめられるようにします。

## 出典の記録

素材ごとに次を記録します。記録先は素材のディレクトリのREADME（例: `assets/README.md`）か、projectが決めた台帳です。

- 入手元: 作成者、サイト・サービス名、URLまたは素材ID、入手日。
- 利用条件: ライセンス名、商用利用・改変・再配布の可否、クレジット表記の要否。確認できない項目は「未確認」と書く。
- 生成素材: AIや手続きで生成した場合は、生成ツール、生成の方法（自作の合成ならseed・パラメータ）、ツールの利用規約上の扱い。
- 加工: 縮小・切り抜き・合成など、元の素材から変えた内容。

## 判断と確認

- 有料素材、利用条件が不明な素材、第三者の作品は、利用してよいかを人間に確認してから追加する。
- 参考として渡された画像・GIF・動画は外観の参考にとどめ、それ自体をcommitしない。
- 配布物に含められない素材、ライセンス上commitできない素材をrepositoryへ入れない。
- 署名付きURL、アカウント情報、API tokenを出典の記録やコードに残さない（[Sensitive data](sensitive-data.md)）。
- 外部サービスから素材を取得する操作は、外部送信やアカウント利用を伴うため[Safety](safety.md)に従う。
- デザインツールから書き出した素材も同じく記録する。デザインファイル自体の扱いは[UI visual](ui-visual.md)に従う。
- クレジット表記・ライセンス文が必要な素材は、記録をもとに[Credits](credits.md)に従って表示する。

## 置き場所

- frameworkやエンジンの慣習と、projectの既存の配置に従う。例: Next.js・Viteの`public/`はそのままのURLで配信され、コードからimportする素材はbuildでハッシュ付きの名前になる。Godotは`res://`配下、Unityは`Assets/`配下。
- 既存の配置がなく新しく決める場合は、計画に配置を書いて確認する。
- 既存の素材の移動・名前変更は、参照（コード、scene・prefab、CSS、公開URL、外部からのリンク）が切れるため、今回の目的に必要なものだけにする。それ以外は別の計画にする。
- Godot・Unityの素材は、エディタ上で移動・名前変更し、`.uid`・`.import`・`.meta`を一緒に動かす。

## ファイル名

AIが新しく追加・書き出しする素材と静的ファイルの名前に適用します。
ソースコードのファイル名は、言語・エンジンの規約（Unityのscriptはclass名と同じ、等）に従います。

- 使う文字は、半角英小文字・数字・`-`・`_`と、拡張子の前の`.`だけにする。拡張子も小文字にする。
- 次の文字を使わない。
  - 日本語などの2バイト文字・全角文字・絵文字。URLでは`%E3%81...`のような表記になり、macOSとLinuxで文字の内部表現（Unicodeの正規化）が違うため、Gitで別のファイルとして扱われることがある。
  - 空白。URLやshellの引数で区切りとして扱われ、引用符の付け忘れで壊れる。
  - 記号（`# ? % & + : ; , ' " ( ) [ ] @ !`等）。URL・shell・Windowsで特別な意味を持つ。Windowsでは`< > : " / \ | ? *`を使えず、`CON`・`NUL`・`COM1`等の名前と、末尾の`.`・空白も使えない。
- 大文字を使わない。macOS・Windowsは既定で大文字小文字を区別しないため、手元では動いても、区別するLinuxのserverやCDNで404になる。
  - 大文字小文字だけが違う名前を同じdirectoryに作らない。
  - 既存のファイルの大文字小文字だけを変える場合は、区別しないファイルシステムでGitが変更を検出しないことがあるため、`git mv`で一度別の名前を経由する。
- 単語の区切りはprojectの既存の流儀（`kebab-case`か`snake_case`）に従う。ない場合は、Webは`kebab-case`、Godotは公式の推奨どおり`snake_case`を提案する。
- 中身が分かる名前にし、種類・対象・状態の順に並べる（例: `enemy_slime_walk_01.png`、`bg-title-dark.webp`、`se_jump.ogg`）。連番は桁をそろえる（`01`、`02`）。
- 版の管理はGitで行う。`final`・`new`・`v2`・日付・「最新」をファイル名に付けない。
- 配信用のハッシュはbuild toolが付ける。元のファイル名に手で付けない（[Web delivery](web-delivery.md)）。
- 日本語の表示名（曲名・キャラクター名等）は、データ・画面・クレジットに書き、ファイル名にしない。
- 受け取った素材の名前が上の条件に合わない場合は、追加するときに名前を変え、元の名前を出典の記録に残す。
- 既存の素材で条件に合わない名前を見つけた場合は、一括で変えず、一覧にして報告する。公開URLや外部からのリンクが変わるため、変えるかは人間が決める。
- 完了前に、追加・変更したファイルの名前が条件に合うことと、大文字小文字だけが違う名前がないことを確かめる（例: 素材のdirectoryに絞って`git ls-files <dir> | LC_ALL=C grep '[^a-z0-9._/-]'`、大文字小文字だけの違いは`git ls-files | sort -f | uniq -di`）。

## 大きなファイル

- commitする前に、追加・変更するファイルのサイズを確かめる。
- 1ファイルが目安を超える場合、AIはcommitせず、次の選択肢を示して人間に選んでもらう。目安はステアリング`tech.md`の「素材」に従い、記載がなければ10MBとする。この10MBは仮の調整値（[Workflow](workflow.md)）として扱う。
  - 縮小・圧縮する（下の「素材の加工」と[Performance](performance.md)に従う）。
  - Git LFSで管理する。clone・CIでLFSの取得が必要になることと、hosting先の容量・転送量の上限と料金を示す。
  - 外部ストレージ（S3・R2・Google Drive等）に置く。repositoryには取得の手順かscriptと、ファイルの一覧とハッシュを置く。署名付きURL・認証情報は残さない（[Sensitive data](sensitive-data.md)）。
  - repositoryに入れない（buildで作れるもの、生成物、手元だけで使うもの）。`.gitignore`に加える。
- GitHubは50MBを超えるファイルで警告し、100MBを超えるファイルを拒否する。一度commitしたファイルは、PRのbranchであっても、消すのに履歴の書き換えが要る。そのため、commitの前に確かめる。
- Git LFSの導入（`git lfs track`と`.gitattributes`の変更）は、repositoryの設定の変更として計画で承認を得る。既存の履歴をLFSへ移す`git lfs migrate`や、履歴から大きなファイルを消す操作は、履歴の書き換えとして[Git](git.md)・[Safety](safety.md)のASKに従う。
- 目安以下でも頻繁に変わる大きなbinary（動画・音声のマスター、3Dのscene等）は、変更のたびに履歴が増えることを計画に書く。

## 元データと書き出したファイル

- 元データ（`.psd`・`.kra`・`.aseprite`・`.xcf`・`.blend`・DAWのproject・未圧縮の音声等）と、配信・ゲームで使う書き出し（`.png`・`.webp`・`.glb`・`.ogg`等）を別の場所に置く。
- 元データを、配信されるdirectory（`public/`等）や、そのまま配布物に入る場所に置かない。非表示のレイヤーや未公開の内容まで公開される。Godotでは`.gdignore`を置いたdirectoryかprojectの外、Unityでは`Assets/`の外に置く（エディタで直接importすると決めた場合を除く）。
- 元データをrepositoryに入れるかは人間が決める（大きい場合は「大きなファイル」に従う）。入れない場合は、置き場所を出典の記録に書く。
- 元データを上書きしない。書き出しは元データから作り直せるようにし、書き出しの設定（サイズ・形式・品質・使ったtool）を出典の記録に書く。書き出しをscriptで行う場合は、scriptをrepositoryに置く。
- AIはbinaryの元データを直接編集しない。編集が必要なら、下の「素材の加工」に従って人間に選んでもらう。

## 使っていない素材

- 未使用と判断する前に、コード、scene・prefab、CSS、データファイル（JSON等）、翻訳ファイルからの参照を検索する。
- 文字列を組み立てたpath（`load("res://" + name)`、`Resources.Load`、CMSのデータ）、公開URLへの外部からのリンク、メール・OGPからの参照は、検索で見つからない。これらがあり得る場合は未使用と断定せず、確認できた範囲を書く。
- 今回の変更で参照されなくなった素材は、[Principles](principles.md)の「置き換えと片付け」に従い同じ変更で削除し、完了報告に挙げる。
- 今回の変更と無関係な未使用の素材は削除せず、path・サイズ・検索の根拠を一覧にして報告する。削除は別の計画にする。

## 素材の加工

頂点の削減・リトポロジー・リグ・UV、画像の描き直し・解像度の変更、音声の音量調整・ノイズ除去など、
素材の品質を左右する加工は、Blender・画像編集ソフト・DAWなどの専用ツールで人間が行う方が、品質を保ちやすく早いことが多いです。
AIはこうした加工を自分で始める前に、次を人間に示して選んでもらいます。

1. 問題を数値で示す: 頂点数・ポリゴン数、ファイルサイズ、解像度、再生時間、ロード時間・描画負荷など、測った値と目安にした上限。
2. 選択肢と影響を示す。
   - 人間が専用ツールで加工する: 必要な作業（例: リトポロジーして5,000頂点以下にする、リグを付け直す）と、加工後の受け取り方。
   - AIがスクリプトで加工する: 使う方法（例: decimate）と、形・UV・法線・リグ・アニメーションが崩れるリスク。
   - エンジンや配布側の設定で対応する: LOD、import設定、圧縮設定など、素材そのものを変えない方法。
3. 推奨案とその理由を示し、人間が選ぶまで素材を加工しない。

頂点数や解像度の上限は、根拠となる仕様がなければ「仮の調整値」（[Workflow](workflow.md)）として扱い、計画と完了報告に一覧で示します。
AIが加工する場合も、元の素材を上書きしません。加工したものは別ファイルにし、出典の記録の「加工」に方法と前後の数値を書きます。
見た目・動き・音の確認は、自動検証とは別に人間確認として報告します。
[Runtime verification](runtime-verification.md)の対象では、その必須検証が人間確認より優先し、未実施ならBlockedとします。
音声では、再生されることとerror・warningがないことが必須検証に当たり、聞こえ方・音量の好みが人間確認に残ります。

完了報告では、追加・変更した素材と、利用条件で未確認の項目を人間の確認事項として挙げます。
