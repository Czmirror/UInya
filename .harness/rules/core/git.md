# Git safety

最重要: 人間や他のAIによる既存変更を、勝手に破棄・上書き・移動しません。

## 作業開始時のリモート確認と取り込み

実装を始める前（別sessionで再開するときも）、次の順で同期状態を確認します。

1. `git status`とdiffで既存変更を把握し、現在のbranch、upstream、作業の基点branchを確認する。
   `origin/main`を決め打ちせず、設定済みのremoteとprojectの運用を使う。
2. 許可されたネットワーク・認証の範囲で、対象remoteを`git fetch`して更新を取得する。
   fetchは作業ファイルへの取り込みではない。remote URLや追跡設定を勝手に変更しない。
3. localと取得済みの追跡branchの差分・ahead/behindを確認する。
   新しい作業branchを作る場合は、基点branchの更新も確認してから起点を選ぶ。
4. 既存変更がなく、対象branchが明確で、localが追跡branchより遅れているだけなら、
   `git merge --ff-only`等で取得済みの更新を取り込む。意図しないmerge commitや履歴rewriteを作らない。
   hook・外部送信・認証などのASK条件は別途適用する。
5. 未コミット変更、履歴の分岐、対象の不一致がある場合は、一律に`git pull`しない。
   既存変更を保護し、差分と取り込み方法を確認する。競合の解消には今回の承認範囲を適用し、
   自動stash・reset・rebase・force pushで同期を強制しない。

上記条件を満たすfast-forward取り込みは、承認済み作業の準備として通常操作に含めます。
それ以外のmergeは下の承認ルールに従います。通常の`git pull`の既定動作には依存しません。
未コミット変更がある場合でもfetchと調査は可能ですが、取り込み前にその変更を勝手に移動しません。

remote未設定・upstream未設定の場合は、取り込み対象を推測して設定しません。
fetchが失敗した場合も「最新」と報告せず、対象・理由・未確認範囲を計画に残します。
取り込み判断に依存しない調査は続けられます。最新の内容が必要な実装は、同期できるまで待つか、
人間が明示したローカル版での作業範囲に従います。
計画には対象branchとlocal/remote revision、取得・取り込みの結果（不要・未実施なら理由）を短く記録します。

push直前にも対象remoteをfetchし、差分と承認範囲を再確認します。
確認後の更新は通常pushの競合検出に任せ、拒否されたら再取得して取り込み方法を判断します。
拒否を理由にforce pushへ切り替えません。

## 通常操作

- 開始時に`git status`と対象diffを確認し、既存変更を把握する。
- 新しいbranchを作る場合は、作業対象projectの命名規則（project固有の`AGENTS.md`等）に従う。
  規則が見つからなければ既存branchの慣習に合わせ、慣習もなければ内容を表す名前を選ぶ。
  規則以外で決めた場合は、作成したbranch名と選んだ理由を完了報告に書く。
  共通Harness自身の命名規則を導入先へ持ち込まない。
- 自分の変更だけを明示的にstageし、staged diffとsecrets混入を確認する。
- commitは通常操作。ただしcommit hook・署名・外部連携にASK条件があれば先に承認を得る。
- ユーザー変更を自分のcommitに混ぜない。AI作成の署名・承認を人間のものとして記録しない。

## PRをまとめる

同じ目的の小さなPRが続くと、人が追う量が増え、確認の抜けも起きやすくなります。PRを作る前に次を確認します。

- 同じ目的で開いている自分のPRがあれば、新しいPRを作らず、そのbranchへcommitを追加する。
  作り直す場合は、前のPRを閉じる理由と新しいPRへのリンクを、前のPRに書く。
- submodule・取り込んだライブラリの参照の更新は、更新元の変更がまとまってから（tag・release・mergeのいずれか）1回で行う。
  まとまる前のcommitを参照する場合は、理由をPR本文に書く。
- マージ後に問題が見つかって修正PRを作る場合は、元のPRで抜けていた確認を1行書く。次の計画で同じ確認を入れるためです。

## 承認が必要な操作

push、上記条件以外のmerge、releaseに加え、以下は実行前に個別の対象と影響を説明します。

- `git push --force`、`--force-with-lease`。
- `git reset --hard`、`git clean -fd` / `-fdx`。
- rebase / amend / filter等による既存履歴のrewrite。
- branch削除、tag削除、remote変更。
- 既存変更を移動するstash、変更を破棄するrestore / checkout。

force pushは通常経路に含めず、必要ならleaseによる競合検出を検討します。
clean等はdry-runで対象を確認し、復元方法がない場合は明示します。
無差別破壊に当たる場合は承認があってもDENYです。

CIが生成する使い捨てcheckoutと、人間の作業ディレクトリを区別してください。
CIの清掃操作を、そのままユーザーのworkspaceへ転用しないでください。
