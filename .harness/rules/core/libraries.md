# Libraries and dependencies

依存・外部コードを追加・更新・取り込む場合と、ライブラリへの切り出しの調査・実施を頼まれた場合に適用します。
自分たちで作って公開・配布しているライブラリの保守とやめ方を扱う場合にも適用します。
承認の条件は[Safety](safety.md)を正本とし、このファイルはそれを緩めません。
目的は、依存を足す理由と取り込んだコードの出どころを後から確かめられるようにし、根拠のない共通化を避けることです。

## 導入の判断順

次の順で検討し、前の段で足りない理由を計画に書きます。

1. 標準ライブラリ。
2. projectが既に使っている依存。
3. package managerでの依存追加。
4. vendoring（外部のコードをrepositoryへコピーする）。

- 数行で書ける小さな処理のためだけに依存を足さない。
- 逆に、暗号・日付と時刻・parser・認証など、誤りやすく既存の実績ある実装がある処理を自作しない。
- 候補ごとに、用途、ライセンス、保守状況、既知の脆弱性、間接的な依存の数、install時に動くscriptを、確認できた範囲で示す。
  確認できない項目は「未確認」と書く。複数の候補があれば比較し、推奨と理由を示す。
- 依存の追加・大規模upgrade・vendoringは[Safety](safety.md)のASKに従い、承認されるまで実行しない。

## package managerでの追加

- projectの既存のpackage managerとlockfileを使い、lockfileの変更もcommitする。別のpackage managerを持ち込まない。
- versionの指定方法（固定・範囲）はprojectの既存慣習に合わせる。慣習がなければ計画で提案する。
- 本番で使う依存と、開発・test・buildだけで使う依存を区別する。

## vendoringと別repositoryの取り込み

vendoringは、package managerで入れられない、改変が必要、配布条件で同梱が必要などの理由がある場合だけ使います。
自作の別repositoryをsubmodule・subtree等で取り込む場合も同じ扱いです。

取り込み元ごとに次を記録します。記録先は取り込んだdirectoryのREADMEか、projectが決めた台帳です（[Assets](assets.md)の出典の記録と同じ形）。

- 入手元: URLまたはrepository、version・tag・commit、入手日。
- 利用条件: ライセンス名と、projectの配布条件との関係。確認できない項目は「未確認」と書く。
- 改変: 取り込んだ後に変えた箇所と理由。
- 更新方法: 新しい版を取り込む手順と、改変を再適用する方法。

- ライセンスがprojectの配布条件と合うか分からない場合は、人間に確認してから取り込む。
- 取り込んだコードを直接直すのは必要な場合だけにし、改変箇所を記録して更新時に再適用できるようにする。
- formatter・lint・文字コードの一律変換の対象から外す設定を確認する（[Coding conventions](coding-style.md)の例外）。
- 署名付きURL、token、アカウント情報を記録に残さない（[Sensitive data](sensitive-data.md)）。

配布物に含まれる依存・取り込んだコードのライセンス文・著作権表示は、[Credits](credits.md)に従って表示します。

## ライブラリへの切り出し候補の調査

repository内のコードを、module・package・別repositoryへ切り出せるか調べる作業です。常時の作業にはしません。
人間に頼まれたとき、または計画の調査で同じ知識の重複が見つかったときに、読み取りだけで行います。

候補にする条件は次のとおりです。数値のしきい値は設けません。

- 複数箇所で同じ知識・不変条件を表している。
- 変わる理由が同じで、一緒に変更されてきた。
- 入力・出力・失敗の契約が安定している。
- 業務の状態や外部I/Oに直接依存しない、または依存を契約として切り離せる。
- 切り出した単位だけでtestできる。

1箇所でしか使っていないもの、見た目は似ていても将来別々に変わるものは候補にしません（[Coding principles](principles.md)のYAGNI・DRY）。

報告では、候補ごとに次を示します。

- 対象のfile・symbolと、同じ知識だと言える根拠。
- 切り出し先（repository内のmodule / 別package / 別repository）と、許可する依存方向（[Design boundaries](design.md)）。
- 移行の手間、影響を受ける利用箇所、リスク。
- 推奨。「切り出さない」も選択肢に含める。

調査で見つけた無関係な重複は報告に留めます。切り出しの実装は別の計画として承認を受け、旧実装の扱いは[Coding principles](principles.md)の「置き換えと片付け」に従います。
切り出したpackageの公開は[Release](release.md)に従います。

## 自作ライブラリの保守とやめ方

自分たちで作って公開・配布しているライブラリ（別repository、package、Godotのaddon、Unityのpackage等）に適用します。
目的は、更新が止まったことを使う人が見分けられるようにし、実行環境や依存の新しい版で壊れたことに気づけるようにすることです。

- READMEの先頭に、保守の状態、対応する実行環境の範囲（例: Godot 4.6〜4.7、Node.js 22以上）、最後に動作を確かめた日を書く。状態は次のどれかにする。
  - 保守中: 不具合の修正と機能追加をする。
  - 機能追加なし: 不具合とセキュリティの修正だけをする。
  - 保守終了: 修正しない。代わりのライブラリか、自分で取り込んで保守する方法を書く。
- ライブラリ単体のtestをCIで回す。実行環境や依存の新しい版で壊れていないかを、定期実行（`schedule`）でも確かめる（[CI/CD](cicd.md)）。
- 依存があるライブラリでは、依存の自動更新（Dependabot等）とセキュリティ警告を有効にすることを提案する。GitHub Actionsのactionも対象にする。
  更新はCIが通ってから取り込み、大きなupgradeは[Safety](safety.md)のASKに従う。依存がないライブラリでは、実行環境の版の確認がこれに当たる。
- manifest（`package.json`、`plugin.cfg`等）のversionとtagを一致させ、利用者に見える変更はCHANGELOGに書く（[Release](release.md)）。
- 自作ライブラリを取り込んでいるprojectでは、取り込みを更新するときに取り込み元の状態を見る。
  保守終了になっていれば、置き換えるか自分で保守するかを計画で提案する。
- 保守をやめるときは、READMEを「保守終了」にして代わりを書き、最後のreleaseを出してからGitHubのarchive（読み取り専用にする機能）にする。
  repositoryは消さない（取り込んでいるprojectのsubmoduleや依存が壊れるため）。archiveとpackage公開の取り下げは人間が行い、AIは手順と影響を示す。
- 状態を決めるのは人間。AIは、最後の更新日、未対応のIssue・警告、CIの結果などの事実を示して提案する。
