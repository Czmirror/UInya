# PDF output

アプリやツールがPDFを作る機能（請求書、見積書、帳票、チケット、証明書、レポートのPDF出力、画面の「PDFで保存」等）を追加・変更する場合と、PDFの崩れ・文字化けを調べる場合に適用します。
利用者がuploadしたPDFを受け取る処理（[Security](security.md)のfile upload）と、AIが人に渡す資料としてPDFを作る作業には適用しません。
目的は、画面では正しく見えるのに出力したPDFだけが崩れること、本番の実行環境だけで文字化けすること、PDFから個人情報やserver内の情報が漏れることを防ぐことです。

既存ルールとの分担:

- 見た目の水準と確認の報告は[UI visual](ui-visual.md)。
- フォントファイルの入手元・利用条件・置き場所は[Assets](assets.md)、ライセンス文の表示は[Credits](credits.md)。
- 管理画面からの出力の認可と記録は[Admin screens](admin-screens.md)の「統計・集計・データの出力」。
- 個人情報の置き場所は[Sensitive data](sensitive-data.md)、serverが外部へ接続するときの検証は[Security](security.md)。
- 定期的にまとめて作る処理は[Scheduled jobs](scheduled-jobs.md)。依存の選び方は[Libraries and dependencies](libraries.md)。

## 生成方式

- 方式は、HTML・CSSからheadless browser等でPDFにする方式と、PDFのlibraryで直接描く方式から、projectで決める。既存の方式があればそれに従う。
- 新しく選ぶ場合は、候補と理由（日本語の扱い、縦書きが要るならその対応、表・改ページの作りやすさ、実行環境に要るもの、保守状況）を計画に書き、人間が決める。依存の追加は[Safety](safety.md)のASKに従う。
- 保守が止まったtoolを新しく採用しない（例: `wkhtmltopdf`は2023年にrepositoryがarchiveされた）。
- 生成に時間がかかる、またはページ数が入力で大きく変わる場合は、要求の中で同期的に作らず、非同期の処理にしてできたら知らせる。ページ数・行数の上限とtimeoutを決める。

## 日本語フォント

- 使うフォントをprojectで決め、PDFに埋め込む。実行環境に入っているフォントに頼らない。Docker image・serverless・CIには日本語フォントがないことが多く、手元だけ正しく出る。
- フォントが決まっていなければ、AIは候補（例: Noto Sans JP、BIZ UDゴシック。どちらもSIL Open Font License）を示し、人間が選ぶ。
- 埋め込むフォントは、使った文字だけのsubsetにしてファイルを小さくする（[Performance](performance.md)）。
- フォントの利用条件が、PDFへの埋め込みを許すことを確かめる。SIL Open Font License・IPAフォントライセンスは許す。商用フォントは製品ごとに確かめる。
- test dataに崩れやすい文字を入れる: 漢字・かな・半角カナ・全角英数、記号（①、㈱、〜、－）、人名の異体字（髙、﨑）、フォントに無いことが多い字（𠮷）、改行を含む長い文字列。絵文字を出すかは仕様で決める。
- 出力したPDFで、すべてのフォントが埋め込まれていること（例: `pdffonts`の`emb`の列がすべて`yes`）と、豆腐（□）・文字化けがないことを確かめる。
  本文に使っていないフォントでも、libraryがページの初期設定で入れる既定のフォント（例: Helvetica）が埋め込みなしで残ることがある。図形・QRコード・バーコードを描く部品が、文字を描かなくても自分の既定のフォント（例: Times-Roman）を入れることもある。見た目では気づかないため、一覧で確かめる。
  反対に、フォントに無い字は、フォントが埋め込まれていれば一覧では`yes`のまま豆腐になる。入力の全文字がフォントにあるかを、描く前かtestで確かめる。無い字を含む入力を止めるか置き換えるかは仕様で決める。
- 入力に改行・タブ等の制御文字が入ったときの扱い（止める、置き換える、改行として描く）を決める。そのまま描くと豆腐になることがある。

## 見た目の確認

- 見た目の水準は[UI visual](ui-visual.md)に従う。
- 確かめるのは、ブラウザの画面ではなく、出力したPDFをページごとに画像にしたもの（例: `pdftoppm`）。画面とPDFでは改ページ・余白・フォントが変わる。
- 用紙サイズ・向き・余白を仕様に書く。印刷する書類では、印刷時の拡大縮小の既定で端が切れないかも確かめる。
- ラベル紙・名札・定型の用紙に印刷する帳票では、使う製品の面の寸法と位置、面の端から文字を離す幅（安全な範囲）を仕様に書く。描いた文字・図形の範囲が安全な範囲に収まり互いに重ならないことをtestで確かめる。
  実寸で印刷するよう指定し（例: PDFの`PrintScaling`を`None`。従うかは閲覧ソフト次第なので印刷手順にも書く）、最初の1枚は人が実際の用紙に印刷して位置を確かめる。
- 縦書きでは、長音・括弧・ダッシュの向き、句読点・小書きの仮名の位置、列の頭に置かない字（行頭禁則）、数字・英字の扱い（2桁までは横に並べる等）を仕様で決める。
  libraryが縦書きに対応していない場合は1字ずつ置くことになり、横書きの字形のままになりやすい。ページの画像で確かめ、禁則は文の長さを1字ずつ変えたtestで確かめる。
- QRコード・バーコードには、個人情報を入れずIDなど必要な値だけを入れる。画像から読み取って中身をtestで確かめる。
- 改ページを確かめる: 表の行が途中で切れない、2ページ目以降に表の見出しを繰り返すか、合計欄だけが次のページに送られないか。
- 長い名前・住所、行数の多い明細、0件、ちょうど1ページで終わる件数のdataで、はみ出し・重なりがないことを確かめる。
- 線や枠で描く図（トーナメント表、組織図、グラフ等）では、線・枠・文字が互いに重ならないことも確かめる。要素の数で間隔を割り付けると、要素が多いときだけ重なるため、最小と最大の要素数のdataで見る。
- 完了報告に、確かめたページの画像を添える（[UI visual](ui-visual.md)の「確認と報告」）。

## 権限・保存・個人情報

- 個人情報を含むPDFのダウンロードは、server側で毎回権限を確かめる。URLを知っていれば誰でも取れる形にしない（要求ごとの認可、期限付きのURL）。
- 作ったPDFを保存する場合は、公開されない場所に置き、推測できないIDで参照する。連番や顧客名をURL・保存場所のkeyにしない。
- ファイル名・URL・ログに個人情報を入れない（[Sensitive data](sensitive-data.md)）。ダウンロード時の分かりやすいファイル名は`Content-Disposition`で付け、保存場所のkeyとは分ける。
  応答には`Cache-Control: private, no-store`等を付け、共有のcacheに残さない。
- PDFのmetadata（作成者、作成ソフト、タイトル）に、内部のserver名・担当者名・pathが入っていないか確かめる。
- 保存期間と削除は仕様で決める。法令で保存が求められる書類（請求書等）の期間・形式は、AIが決めずに人間が決める。

### HTMLからPDFを作る場合

描画エンジンは、HTMLに書かれたURLやファイルを読み込みます。利用者の入力値にHTMLを仕込まれると、server内のファイルやmetadata endpoint・社内URLの内容がPDFに写ることがあります（[Security](security.md)の外部接続）。

- 利用者の入力値は、templateの自動escape等でHTMLとして解釈されない形にしてから入れる。
- 描画エンジンからの通信を止めるか、許可したURLだけにする。`file://`も拒否する。フォント・画像はローカルのファイルか埋め込みで渡す。
- JavaScriptが不要なら無効にする。timeoutとページ数の上限を設ける。

## 再現性とtest

- 同じ入力から同じ内容のPDFを作る。作成日時・発行日・番号・乱数は引数で渡し、testで固定できるようにする。
- testでは、PDFからテキストを取り出し（例: `pdftotext`）、金額・宛名・日付・ページ数などの主要な値を確かめる。
  byte列を丸ごと比べるtestは、作成日時等で変わるため既定にしない。
  図のように文字が離れて置かれるPDFでは、取り出したテキストの並び順で近くの別の文字（スコア等）が間に入ることがある。描いた順で取り出す（例: `pdftotext -raw`）か、範囲を絞って取り出して確かめる。
- 金額の書式・端数処理・税の計算と、書類に必ず書く事項（請求書の記載事項等）は、AIが決めずに仕様に書く（[Input validation](input-validation.md)）。
- testは、崩れやすい文字、改ページの境界（ちょうど1ページ、1行だけあふれる）、0件、上限を超える要求、権限のない人のダウンロードの拒否を含める。
  境界の件数は手で探さず、明細を1件ずつ増やしてページ数が増える件数をtestで求め、その直前の件数と求めた件数で確かめる。帳票の見た目を変えると境界も動くため、件数を固定で書かない。

確かめ方の例に挙げた`pdffonts`・`pdftotext`・`pdftoppm`（poppler）は必須ではありません。projectの言語のlibraryで同じことを確かめても構いません。

## 扱わないこと

- PDF/A（長期保存の形式）、電子署名、タグ付きPDF（読み上げ対応）、電子帳簿保存法への対応は、必要かをprojectの仕様で決める。要件に出てきたら、AIは確かめるべきこととして人間に示す。
- 個別のlibrary・toolの使い方。
